# The accepted spec is the handoff; it merges first, with a status per criterion

Brainstorming and shaping happen outside the factory. An owner chat in the target repo (`just shape`: Pi with only the shaping skills, grill-with-docs, improve-codebase-architecture, sharpen and spec-chat-shape, never a factory role; or Exo) shapes the spec with `spec-chat-shape`, commits the spec on branch `spec/<slug>`, pushes it, and registers it with the review service under `--slug <spec slug>`; no issue exists yet. Gate 1 is the owner pressing Accept spec: the acceptance is the hand-off the review page writes on that press, when it is the spool's newest hand-off and the version it accepted is the spec at the review-host row's `base` commit (the exact commit). An Accept of any other text of the spec, or one followed by a comment hand-off, is not one. Decided by Tom (owner), 2026-10-18 and 2026-10-20. The button is the only way to accept a spec: an acceptance said in chat is not one, and no agent records one on the owner's behalf. Decided by Tom (owner), 2026-10-19.

Kickoff: the owner tells the director "build <spec path>" (one spec or several), with a kickoff brief from the kit's `docs/kickoff-brief.md` (target, accepted spec and commit, the project's tooling, gate, QA path, deadline; the director merges nothing). Brief by Tom (owner), 2026-10-20. The director runs `octo-feather-accepted`, which reads every session's review-host registry and refuses any spec not accepted at a commit present in the target repo, saying why. For each accepted spec the director opens a small spec PR before any lane code: branch `spec/<slug>` at the accepted commit plus one commit adding the status file, every criterion `planned`, its body citing the Spec Chat acceptance id and commit. The owner merges it, since merges are an owner gate. Lanes are cut (ADR 0019) and branched from main once their spec is on it. Decided by Tom (owner), 2026-10-19.

Status lives beside the spec, never in it: `docs/specs/<slug>.status.json` is `{"spec": "<slug>.spec.html", "accepted_commit": "<sha>", "criteria": {"<id>": {"status": "planned" | "built", "pr": <N or null>}}}`, where a criterion id is the `data-anchor` of each `data-acceptance-criterion` element (Spec Chat's shaped-sections-v1 contract). The accepted spec HTML stays byte-identical, and Spec Chat stays workflow-agnostic. `scripts/octo-feather-spec-status` writes it (`init`, `built`) and checks it (`check`, inside `just check`): ids exactly match the spec's, none missing, extra or duplicated, statuses only `planned` or `built`, and a `built` criterion names its PR. Each lane PR flips only its own criteria to `built`, in the same merge as its code, and its merge ask lists the criteria it flips; the flip is written by `just qc` for the criteria it passed (ADR 0022). Decided by Tom (owner), 2026-10-19.

Accept freezes the spec. No agent edits an accepted spec, or one with a live review row, without a fresh owner ask relayed by the director, wording-only fixes included. Before editing a spec with a live review row, the editor runs spec-chat-review's read-only reconnect scan on the spec's directory (`watch-specs.sh <spec dir> .cursor-owner 0 3`): exit 0 lists a pending hand-off (a comment batch or an Accept) that is reconciled first, and an Accept found there freezes the spec; only exit 3 (empty backlog) clears the edit. Decided by Tom (owner), 2026-10-19, after finding 20 (lane #8): commit 44c4c92 landed on issue-lifecycle 20 seconds after the owner's Accept, unscanned, and voided it.

The supervisor never shapes. A wording-only spec fix, once the owner says yes to its fresh ask, rides on the acceptance (renaming a criterion anchor renames its status key in the same commit); a behavior change gets a spec revision (`spec-chat-shape`, its only use there) whose review link goes up through the director before any merge ask, naming the criterion ids it affects, directly or through a clause that governs them; its acceptance moves `accepted_commit`, resets those criteria to `planned`, adds new ones as `planned` and drops removed ones. A work item whose behavior the spec on main already states goes straight to a lane. Decided by Tom (owner), 2026-10-19.

## Considered options

- The supervisor shapes inside its lane (octo-lite). Rejected: shaping is a conversation with the owner, and only the director talks to the owner (ADR 0015); a lane would exist before anyone knows how to cut it (ADR 0019).
- The director records an acceptance receipt comment on each lane PR, and the spec reaches main with the first lane. Rejected: the acceptance is scattered across lane PRs, and main never says which criteria are built.
- The director records an acceptance the owner gives in chat. Rejected: a second path to the same gate, and an agent writing the owner's decision.
- Status inside the spec HTML (an attribute per criterion). Rejected: the accepted bytes would change, and Spec Chat would have to know this workflow.

## Consequences

- A baseline `just qc` run against criteria already on main logs each failure as a `"kind": "gap"` line and opens a gap lane, never a correction lane (docs/adr/0020, finding 21).
- The freeze binds every role that can edit a spec: the supervisor asks before any spec commit and scans the spool; implementers and correctors never edit `docs/specs/*.spec.html`; the code reviewer blocks a diff that edits an accepted spec with no owner yes named in the PR body.
- The director's role file holds the kickoff check and the spec PR; the supervisor's holds the status flip and the merge ask's criteria list. No role records a receipt.
- `octo-feather-accepted` and `octo-feather-spec-status` are tested in `just check`. `octo-feather-accepted` reads Spec Chat's registry files and spool hand-offs directly, since review-host has no query command, and recomputes Spec Chat's served-page version for the spec at `base`; `tests/accepted.sh` pins that version against Spec Chat's own, so a format change breaks it loudly. A registry `accepted` key counts for nothing, so a hand edit cannot accept. This guards against accidents, not attacks: Spec Chat refuses agent writes to the human spool over HTTP and no role writes there, but any local process could.
- Spec Chat infers lanes from slug shape (docs/future.md, "Spec Chat assumes a lane-key workflow").
