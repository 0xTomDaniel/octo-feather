# Integration and end-to-end tests only

Tests are integration or end-to-end and never unit-test internals. An end-to-end test, and `just qc` with the QA demos that validate spec criteria, drive only a public interface the product offers its users (its CLI, HTTP, UI, MCP or another public protocol), with machine-readable output such as `--json` where it offers it. A target with no public interface uses its runnable script (`harness.py` in pilot 1) as its end-to-end and QA path; a target with no runnable script either has no end-to-end test, and its PR says QA does not apply. An integration test drives a seam, the interface where you observe behavior without reaching inside (the `tdd` skill), of any module, public or internal, under two hard requirements: the module is deep with a stable interface (never a private helper, never a shallow wrapper whose interface mirrors its implementation), and the seam was written down from the ticket's acceptance criteria before any test, so review can check each test against that list. It stands in only at external boundaries. When no deep module with a stable interface exists at the seam a criterion needs, the implementer deepens the product code first as its own step: pin current behavior (the `refactoring` skill, step 1), deepen the module (the `codebase-design` skill's DEEPENING.md), then test at the new interface. Each acceptance criterion gets one or two tests, run against the repo's real data files where they exist, so the suite stays small. Nothing only a test uses lives in production code: no test-only flag, env var, hook, parameter or branch; a test reaches a hard state by mocking at the boundary. Product code changed to give a real deep interface is no test leak. Agents rewrite internals freely, so tests pinned to shallow internals break on every refactor and prove little about behavior; a deep module's stable interface survives those rewrites. Code review blocks a test at a shallow seam or at a seam missing from the written list. Decided by Tom, 2026-10-18 and 2026-10-20; the seam rule, both guards and the deepen-first step by Tom, 2026-11-12 (issue #795).

The vendored `tdd` skill is patched to match: before writing any test, the implementer writes down the seams under test, each the interface of a deep module with a stable interface, taken from the ticket's acceptance criteria, one or two tests each, and confirms with the supervisor any seam the ticket does not name; the list goes where review reads it (a comment on the ticket) before the first test commit. The patch also names the test leak as an anti-pattern. The `codebase-design` DEEPENING patch tests a deepened module at its new interface once it is deep and stable. Approved by Tom, 2026-10-18, 2026-10-20 and 2026-11-12.

The kinds above are amended in place by the 2026-11-19 owner ruling (issue #1084), recorded in quality.calls.jsonl: what makes a test integration or end-to-end, and that an eval is never a test, is owned by [quality#test-kinds](../specs/quality.spec.html#test-kinds); the seam rules above say where a test enters, not which kind it is.
