# A finite host-cleanup worker uses a task contract through the existing launcher

A product implementer's isolation contract is the wrong authority for host cleanup. Use a fresh cleanup contract kind through the existing launch seam, with the director as its parent. A kit-owned fixed ceiling outside the standing-role catalog keeps validation centralized without adding a standing role selectable by --role; the director supplies bounded task data rather than authoring policy. See see [task-scoped launch](../specs/host-cleanup.spec.html#acceptance-task-scoped-worker), [parent routing](../specs/host-cleanup.spec.html#acceptance-task-worker-route), and [protected data](../specs/host-cleanup.spec.html#acceptance-cleanup-protected-data). This supersedes only the named-specialist-profile requirement of ADRs [0013](0013-role-files-are-pi-subagents-agents.md) and [0016](0016-every-agent-launches-through-pi-role.md), and the mandatory intervening supervisor in [0015](0015-escalations-go-up-the-chain.md), for this finite non-product assignment.

An uncontracted native launch would discard the controls that make delegation safe; widening an existing implementer would discard product isolation. Both are rejected. Keeping the same launcher and a fresh explicit contract permits the authorized operation without a new runtime, a standing maintenance role, or a change to product-lane ownership.
