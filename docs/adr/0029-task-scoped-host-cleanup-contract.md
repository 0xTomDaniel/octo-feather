# A finite host-cleanup worker uses a task contract through the existing launcher

A product implementer's isolation contract is the wrong authority for host cleanup, but requiring a permanent specialist profile for a one-off operation makes delegation depend on the installed role catalog. Use a fresh task-scoped host-cleanup contract through the existing launch seam, with the director as its parent: see [task-scoped launch](../specs/host-cleanup.spec.html#acceptance-task-scoped-worker), [parent routing](../specs/host-cleanup.spec.html#acceptance-task-worker-route), and [protected data](../specs/host-cleanup.spec.html#acceptance-cleanup-protected-data). This supersedes only the named-specialist-profile requirement of ADRs [0013](0013-role-files-are-pi-subagents-agents.md) and [0016](0016-every-agent-launches-through-pi-role.md), and the mandatory intervening supervisor in [0015](0015-escalations-go-up-the-chain.md), for this finite non-product assignment.

An uncontracted native launch would discard the controls that make delegation safe; widening an existing implementer would discard product isolation. Both are rejected. Keeping the same launcher and a fresh explicit contract permits the authorized operation without a new runtime, a standing maintenance role, or a change to product-lane ownership.
