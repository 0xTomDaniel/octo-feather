Host cleanup

docs / specs / host-cleanup.spec.html

One finite, explicitly authorized host-cleanup operation, delegated to a fresh Pi worker under a task-fitting contract. The director is its parent; a product implementer's isolation is never widened. This contract owns only that non-product operation, not general ad hoc agents, product workflows or the parent-notification policy. The scoped launch decision is ADR 0029.

User stories

As the owner, my director delegates authorized host cleanup to a fresh task-fitting executor without selecting a standing specialist or asking me for another routine cleanup Go.

As the owner, I get an accounted cleanup outcome that preserves live and parked work, leases and evidence and credits only verified removals.

Acceptance criteria

Given a director with a fixture to be added containing authorized host maintenance and an available implementer restricted to product-worktree writes, When the director prepares the delegation, Then the mismatch is identified before dispatch, without assigning host writes to that implementer or asking for routine approval to override its contract.

Given a director with a fixture to be added containing authorized host cleanup and admitted worker capacity, When the director delegates that finite task without selecting a named specialist role, Then a fresh Pi worker starts under a host-cleanup contract with the director as parent and the authorized GPT model from its first process, without inheriting an unrelated implementer contract.

Given a director with a fixture to be added containing a cleanup contract requesting product-edit capabilities, When the director submits that contract for launch, Then launch is refused before an executor starts, naming the authority mismatch.

Given a host-cleanup worker with a fixture to be added containing a reachable director parent and a peer lane, When the worker tries to send its result to that peer lane, Then the message is refused as outside its parent route, without treating the missing specialist role name as unrestricted messaging authority.

Given a host-cleanup worker with a fixture to be added containing an active evidence lease inside its inventory scope, When the worker inventories that candidate then completes its bounded cleanup assignment, Then the leased evidence is retained and the result identifies its protection, without treating cleanup intent as release authority.

Given a host-cleanup worker with a fixture to be added containing verified unused unleased scratch inside its permitted deletion scope, When the worker performs its cleanup assignment, Then eligible scratch is removed and the director receives an itemized outcome with measured free-space change, without an extra routine approval gate.

Given a host-cleanup worker with a fixture to be added containing a completed result and an unreachable director parent, When the worker attempts its required return, Then the result remains recoverable under its worker identity with the delivery failure recorded, rather than being lost, sent to a peer or treated as consumed.

Modular boundaries

The cleanup executor owns bounded inventory, eligible removals and its itemized result; the director owns task scope, actual admission and result consumption. The caller-facing seam is a finite cleanup contract through existing herdr-spawn/pi-role and the existing parent result route. Dependency direction: cleanup calls the kit launcher, which uses external-provider Pi/Herdr surfaces; current ownership/lease evidence constrains removal, and product lanes do not depend on this execution contract. Observable scope: a fresh authorized worker, protected candidates retained, verified eligible removals and an accounted terminal result.

Task-scoped host cleanup

For explicitly authorized host cleanup, the director launches a fresh worker without selecting a named specialist role or creating a permanent maintenance role. The same controlled herdr-spawn/pi-role seam applies the task contract, rather than appending permissions to an unrelated worker's contract. A new independent operation never reuses an unrelated worker session.

The launcher validates the cleanup-specific authority ceiling before starting any process. Task parameters can narrow roots, candidates, tools and budgets, not grant product edits, a different runtime, an unauthorized model or unrestricted routes. Missing or invalid scope, parent, runtime or tool authority fails closed before dispatch. Worker-class parent-routing restrictions apply without relying on a specialist role name.

The director records the assignment, worker identity, unresolved need and consumed result using its existing note facility and the native conversation. A bounded wait stays with that identity; this contract introduces no director-parented parking mechanism. An unreachable parent or uncertain send leaves the result recoverable and unconsumed, never authorizes a peer route or a fallback to the same unreachable director. Replacement requires reconciling partial removals and late results and ending the prior writer's authority first.

No agent launches uncontracted or bypasses the controlled launcher. If a candidate needs access, ownership release or a destructive-risk decision outside admitted authority, retain it and identify that exact missing action and its authority holder. Do not turn the already-authorized cleanup into another routine permission request. Spec acceptance permits factory delivery of this contract, not immediate use of an unavailable launch mode or unverified host deletion. Product worker isolation, supervisor PR/integration ownership, owner merge gates and existing provider recovery remain unchanged.
