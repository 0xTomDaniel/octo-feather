octo-feather: a light software factory kit

docs / specs / overview.spec.html

octo-feather is a stack-agnostic kit that turns a spec the owner shaped and accepted outside it into finished, verified work, one pull request per lane, with the owner deciding only at gates. Terms are defined once in GLOSSARY.md; lasting decisions are the ADRs in docs/adr/, which win over this page where they differ.

User stories

As the owner, I hand the factory an accepted spec and get back one pull request per lane with verified work, deciding only at the spec and merge gates, without writing code.

As the owner reading any kit text, I see one vocabulary (owner, director, supervisor, worker, lane), so no retired role name hides an old behavior.

As a builder porting the kit onto Exomachina or another runtime, I replace the launch scripts and the herdr-comms skill and edit only the transport commands named in role files; role responsibilities, briefs, log formats, specs and ADRs carry over unchanged.

As the owner, I run one agent runtime, so there is one spawn path, one set of role contracts and one model route.

Acceptance criteria

Given the owner with an accepted spec, When the owner tells the director to build it, then the director relays a lane's merge ask, Then the owner sees that lane's one pull request holding every ticket's work, a code-review verdict and passing required checks, and the owner has edited no file.

Given a maintainer, When any change adds kit text outside GLOSSARY.md and vendored skills that calls the top agent operator or the person human, Then the gate fails and its message says to use director for the top agent and owner for the person.

Given a maintainer, When any change adds a Claude or Codex instruction file or projection to the kit, Then the gate fails naming Pi as the only runtime.

Given a builder replacing the Pi and Herdr launch wiring with another runtime's launcher, When every role is started through the new launcher, Then each role runs its file's model, tools, skills and contract, the only role-file edits are to the transport commands they name, and no brief, log format, spec or ADR was edited for the port.

Modular boundaries

The kit owns the role files, its own and vendored skills, the launch and integration scripts, and its gate. Caller-facing seam: the justfile recipes (just start, just supervise N, just integrate N, just check) and the role files in agents/. Dependency direction: external-provider; the kit depends on Pi, Herdr, GitHub, Spec Chat and the remote host, and none of them depends on the kit. Observable scope: Herdr workspaces and tabs, GitHub issues and pull requests, and gate output.

A target repository owns its product, its AGENTS.md, its own just check, and its specs. Caller-facing seam: the target's AGENTS.md, which every role loads from its working directory, and its just check. Dependency direction: self-contained; the target names no kit path, and the kit depends only on these seams. Observable scope: commits, the target's gate, and its app CLI.

The factory

The director edits no code or spec and never shapes; its only repo write is the spec pull request's generated status file (ADR 0007). It takes an accepted spec at kickoff, opens its spec pull request, cuts lanes once the spec is on main, files each lane's parent issue, starts one supervisor per lane, starts correction lanes on repeats, removes blockers and brings the owner only gate decisions.

Shaping and spec acceptance happen outside the factory, in the owner's own chat; the accepted spec, at an exact commit, is the only thing handed in (ADR 0021).

Every lane gets a supervisor, even when it is the only one running: one lane is one merge ask on one parent issue. The supervisor files the lane's tickets, directs its workers, runs implementers in parallel whenever ready tickets allow and it judges it practical, and never does their work, reviews it, or accepts it.

Runtime-neutral data, isolated launch wiring

The kit keeps everything an agent needs as plain data, and keeps every Pi or Herdr specific step in a few launch scripts and the herdr-comms skill, so a port to Exomachina swaps those and edits only the transport commands role files name.
