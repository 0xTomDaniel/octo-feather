Spikes and prototypes: exploring before Accept

docs / specs / prototyping.spec.html

While a spec is being shaped, the owner may explore with running code: a spike, a throwaway prototype or an evolutionary prototype (GLOSSARY.md). A prototyper writes that code for the shaper, who never does. Disposable code never reaches the product; an evolutionary prototype reaches main only by promotion in a build lane, under the full gate, review and QC (ADR 0032). What happens after Accept is in issue-lifecycle; the roles are in roles.

User stories

As the owner, I point at a part of the running interface, write a note and watch it change, with no round, video or batch to wait on, so I stay in flow while I tune it.

As the owner, the interface I tuned is the starting point of the build, so what ships is what I tuned and nobody redraws it from a description or a picture.

As the owner, I ask for a spike or a throwaway prototype to answer one question fast, with no process around it, and get the answer written down while its code never reaches the product.

As the owner, I accept an interface from a frozen copy of it, so what I accept cannot change under me.

As the owner, no code written before I accept reaches main's tree without the gate, review and QC, so exploring fast never lowers the product's standards.

As the owner, nothing I press in a prototype reaches real data or a real service.

As the shaper, a prototyper writes the code and tells me only discoveries, blockers and decisions that need shaping, so my conversation stays on the spec.

As a supervisor building an accepted spec, I get the spec and its accepted prototype, and nothing of the conversation that shaped them.

Acceptance criteria

Given the owner on a desktop with a live session on a web screen's evolutionary prototype, When the owner points at a part of the running screen, then writes a note and sends it, Then the running screen shows the change the note asked for, and the owner pressed nothing more to see it.

Given the owner with a live session whose prototyper is partway through a change, When the owner sends a second note, Then the running screen shows both changes, the second after the first.

Given the owner with a live session whose notes are all settled, When the owner asks to review the screen for acceptance, Then the review link opens the screen served from the frozen candidate, and the page names the candidate it shows.

Given the owner with a live session holding a note that is not yet settled, When the owner asks to review the screen for acceptance, Then the answer refuses to freeze and names the unsettled note.

Given the owner reviewing a frozen candidate, When the owner sends a new note on its screen, then asks the shaper for the session's state, Then the shaper answers that the session is live again and that candidate is withdrawn.

Given a director at kickoff with a spec accepted together with an evolutionary prototype, When the director opens the spec pull request, Then the pull request's changed files are the spec's artifacts and its status file, and none of the prototype's code.

Given a director at kickoff with a spec accepted together with an evolutionary prototype, in a target repository that does not allow merge commits, When the director runs the kickoff check, Then the check refuses the kickoff and names the repository setting to change.

Given a supervisor whose lane owns an accepted evolutionary prototype, When the supervisor promotes it in the lane's first ticket, Then the lane's draft pull request shows the accepted prototype's whole change, applied on current main, as its first commit.

Given a supervisor whose lane owns an accepted evolutionary prototype, with main changed since Accept in a file the prototype changed, When the supervisor promotes it, Then the promotion stops, naming each conflicting file, and the lane branch is where it was before.

Given a supervisor whose lane promoted and then hardened an accepted evolutionary prototype, When the supervisor runs QC on the lane's head, Then QC's record compares each step of the screen's walkthrough on the built screen with the accepted prototype, and names each step that differs.

Given the owner shaping a spec with a shaper, When the owner asks for a spike on a technical question and waits for it to finish, Then the shaper shows the owner its findings: the question, what was seen, the limits and the conclusion.

Given a maintainer of a target repository whose shaping session ran a spike to its end, When the maintainer lists the repository's branches and worktrees, Then the list holds the shaping branch and nothing from the spike.

Given a supervisor whose lane's spec was shaped with a throwaway prototype, When the supervisor asks the kit to promote that prototype's code, Then the kit refuses, saying a spike and a throwaway prototype have no promotion.

Given the owner with a live session on a prototype whose screen saves a value, When the owner saves a new value, then asks for the prototype to be restarted, then opens the screen, Then the screen shows the fixture's own value, not the one the owner saved.

Given a shaper parenting a prototyper in a live session, When the prototyper finds that a behavior the spec states cannot work as written, Then the shaper receives one message naming the discovery and the decision it needs.

Given a shaper parenting a prototyper in a live session, When the prototyper makes the edits the owner's notes ask for, Then the shaper's conversation still ends at its last exchange with the owner, with no message about those edits.

Given a supervisor starting a lane from a spec accepted together with an evolutionary prototype, When the supervisor reads its kickoff, Then the kickoff names the spec, its accepted commit and its prototype, and nothing from the shaping conversation.

Modular boundaries

The prototyper owns the code of a session: a spike, a throwaway prototype or an evolutionary prototype, and running it for the owner. Caller-facing seam: the shaper's brief naming the session's kind and question, the owner's notes, and the messages it sends its parent. Dependency direction: external-provider; it depends on the target's prototype command and on Spec Chat for the owner's notes. Observable scope: the running interface, its commits on the session's own branch, and its messages to the shaper.

The shaper owns the spec, the session's kind and question, and what a session's findings change in the spec; it writes no code. Caller-facing seam: its conversation with the owner, and the brief it gives the prototyper. Dependency direction: self-contained; it reads what the prototyper reports and the running interface, never the prototyper's edits as they happen. Observable scope: the spec, its ADRs and glossary terms on the shaping branch.

Freezing owns the candidate the owner may accept: the shaping branch's commit that holds the spec, its mockup files and the prototype's code together, and the prototype served from it. Caller-facing seam: one kit command the shaper runs, which refuses while a note is unsettled. Dependency direction: external-provider; it reads the prototyper's branch and Spec Chat's record of the session's notes. Observable scope: the candidate commit, the address the frozen prototype answers at, and the session's state, live or frozen.

The spec pull request owns carrying an accepted spec to main without its prototype's code in the tree. Caller-facing seam: the director's kickoff, as issue-lifecycle states it. Dependency direction: external-provider; it depends on the accepted commit and on the target repository allowing merge commits. Observable scope: the pull request's commits and changed files.

Promotion owns bringing an accepted evolutionary prototype's whole change onto a lane branch, once, for one owning lane. Caller-facing seam: one kit command the supervisor runs in a ticket. Dependency direction: self-contained; it reads main's history and writes the lane branch. Observable scope: the lane branch's first commit, or the conflicting files it names.

Spec Chat owns pointing at the running interface, the owner's notes and their threads, the review page and Accept spec. Caller-facing seam: its lane command, its prototype address, its mockup files and its hand-offs. Dependency direction: external-provider; the kit depends on it, and it names nothing of the kit. Observable scope: the review page and what the owner writes on it.

The target repository owns its prototype command and its fixtures. Caller-facing seam: the one command its AGENTS.md names, which serves the interface on fixture data. Dependency direction: external-provider; the kit runs it and depends on its fixtures reaching no real data or service. Observable scope: the interface it serves and the scratch state it keeps.

Three kinds of exploration

A session is one kind, named when it starts, and the kind fixes what happens to its code.

What each kind answers and what becomes of it
KindAnswersJudged byIts codeWhat it leaves
SpikeOne technical question: can this work, does this design holdMeasurement or a testDisposable, in a checkout outside the target's worktreesFindings, written into a spec or an ADR
Throwaway prototypeOne design question: what an interface should look like, whether a flow feels rightThe owner, by seeing or using itDisposable, in a checkout outside the target's worktreesThe decision, written into the spec
Evolutionary prototypeThe interface itself, tuned until it is rightThe owner, by using itRetained on the shaping branch, then promotedThe accepted interface, as code the build starts from

A spike and a throwaway prototype have no promotion: nothing of theirs is copied into the product, and a build lane never reads their checkout.

Retained means reviewed for promotion, never shipped as written: the owning lane hardens each part or rewrites it, and the gate, the review and QC judge the result.

An evolutionary prototype may hold real interaction logic, such as how a control answers a press or keeps focus; everything behind the interface answers from fixtures.

A technical question that comes up inside an evolutionary prototype's session is answered by a spike of its own, in its own checkout.

None of the three needs a spec, an issue or a lane before it starts: the session is how the spec is found (ADR 0032).

Any interface

A prototype is of an interface: anything a person judges by using it, such as a screen, a command line or a voice.

A web screen is the common case and the one this page states in full, because Spec Chat's review page shows web pages.

For any other interface the kinds, the two states, freezing and promotion hold unchanged; the owner's notes come through the shaper's conversation until that interface has a review page.

Who does what

The shaper starts a session by spawning one prototyper and stays its parent for the session's life.

One prototyper role runs all three kinds; what it may write and where differs by kind, and a spike or a throwaway prototype never gains a promotion.

The owner's notes on the running interface reach the prototyper directly, through the pane the session registered with Spec Chat, never through a pane the page names.

The prototyper tells the shaper discoveries, blockers and decisions that need shaping, as they happen, and nothing about its edits.

The shaper and the prototyper each work in a checkout of their own, so neither commits over the other.

The prototyper checks its own change in a browser, with the browsing tool the kit already gives its workers (agent-browser).

Live and frozen

An evolutionary prototype's session is in one of two states.

The two states of an evolutionary prototype's session
StateWhat the owner doesWhat the prototype runs fromLeaves it
LivePoints, writes notes, watches each changeThe prototyper's checkout, changing as it editsThe shaper freezes, once every note is settled
FrozenReviews the spec and the interface, and may press Accept specA clean checkout of the candidate commitA new note from the owner, which makes it live again

Live makes no commit per note, no hand-off batch, no video and no round.

A note is settled when it is implemented, withdrawn, or deferred with the owner's agreement; an acknowledgement settles nothing.

Freezing makes the candidate: one commit on the shaping branch that joins the spec, its mockup files and the prototype's whole change.

A note that arrives while frozen withdraws that candidate; a later freeze makes a new one, and only the newest can be accepted.

From Accept to main

Main's tree never holds code the gate has not passed; an accepted prototype's code stays in main's history until a lane promotes it.

  1. The owner accepts the spec at the candidate commit, which holds the spec, its mockup files and the prototype's code.
  2. The spec pull request is that commit, then one commit that removes exactly the prototype's change, then one commit that adds the status file.
  3. It merges with a merge commit, so the candidate commit stays in main's history and the accepted spec reads the same there.
  4. The owning lane's first ticket promotes the prototype: it undoes the removing commit on the lane branch, which applies the prototype's whole change to current main and names every conflict.
  5. The lane hardens or rewrites each part under the full gate and the review, and QC drives the built screen against the accepted prototype.

One lane owns an accepted prototype's change; a lane that depends on it starts after the owning lane merges.

A target repository that takes specs with prototypes allows merge commits; the kickoff check refuses one that does not, before any spec pull request opens.

QC's comparison is a check that hardening changed nothing the owner tuned; it is no promise to rebuild a screen from pictures.

Safety

Everything behind a prototype's interface answers from the target's fixtures, in scratch state that ends when the prototype stops.

The target's prototype command is what keeps a prototype's writes from reaching real data or a real service; no proxy or page is relied on for it.

A prototype's address is reached as a review page is reached (remote).

Pace

The aim is a change on screen within ten seconds of the owner's note on a plain web app.

The kit's own share, everything but the model's edit, aims at three seconds.

Neither figure fails a gate: the prototyper's model is chosen by its measured edit time, and the owner sees how long each change took.

Open questions

How does a part that lives inside another product's window, such as a plugin, run as an evolutionary prototype? It waits on the measurements from a browser on another machine.

Which way does a live change reach the page the owner points at, when the owner's browser is on another machine? Spec Chat owns the mechanism; this page only needs one that works for a plain web app and for a plugin.
