Remote host and review hosting

docs / specs / remote.spec.html

Where the factory runs: ADR 0005. The owner reviews specs in a browser through Spec Chat's review service, kept private by exe.dev's HTTPS proxy where that proxy is used. Box setup is done once by the box's owner, outside any lane.

User stories

As the owner, I open a spec's review link in an ordinary browser, sign in to exe.dev once, and review and accept the spec, with no SSH tunnel.

As the owner, no one without access to the VM's exe.dev account can read a spec under review.

As the owner, review links keep working after I log out of the VM and after the VM restarts.

As the owner of a Linear target, my Linear key reaches the agents that work tickets from my environment alone, is never written down, and never reaches the product judge.

As the box's owner, the install check tells me when a target's tracker needs a tool the box lacks.

As the box's owner, the install check tells me when a target's verify skill needs a headless browser the box lacks, and one install serves every agent and the product judge.

As the box's owner, the install check tells me when the box lacks agent-browser, the browser CLI the implementer and corrector drive.

Acceptance criteria

Given a visitor not signed in to exe.dev, When the visitor opens a spec's review link, Then the browser shows the exe.dev login page and no spec content.

Given the owner signed in to exe.dev, When the owner opens a spec's review link, Then the spec loads with its review controls, including Accept spec.

Given the box's owner, When any change to box setup or the review service is applied, Then exe.dev still reports the VM's sharing mode as Private and no share link or added user exists.

Given an owner chat that registered a spec for review, When every SSH session to the VM ends, then the owner opens the review link, Then the spec loads.

Given a registered spec, needs an induced failure: the VM restarts, When the VM is back up and the owner opens the review link, Then the spec loads with no one having started the review service by hand.

Given the owner of a Linear target who started the factory with a Linear key in the environment, When a lane's supervisor files the lane's tickets, Then Linear shows the tickets under the lane's parent ticket, and no file in the repository or the factory's state holds the key.

Given a supervisor of a Linear target started with a Linear key in the environment, When it runs just qc on its lane, Then the product judge's run holds no Linear key and reads no Linear ticket.

Given the box's owner with a target that selects Linear on a box without the linear CLI, When the owner runs the install check for that target, Then it lists the linear CLI as missing, naming the pinned version and how to install it.

Given the box's owner with a target whose verify skill drives a headless browser, on a box without that browser, When the owner runs the install check for that target, Then it lists the headless browser as missing, naming the version the target pins and how to install it.

Given the box's owner on a box without agent-browser, When the owner runs the install check, Then it lists agent-browser as missing, naming the release the kit's agent-browser skill is pinned to and how to install it.

Given a supervisor, When any change opens or edits an issue or pull request, Then it holds no review URL.

Modular boundaries

The host owns running every agent, Herdr session, toolchain and the review service. Caller-facing seam: a shell on the host; on an exe.dev VM, SSH to <vm>.exe.xyz and exe.dev's admin commands. Dependency direction: on an exe.dev VM, external-provider; it then depends on exe.dev. Observable scope: the host's services and, on exe.dev, its sharing mode.

Spec Chat's review service owns serving specs, review spools and acceptance. Caller-facing seam: the lane registration command and the review URL. Dependency direction: external-provider; the kit depends on Spec Chat, which names no kit path. Observable scope: the review page and its hand-offs.

exe.dev's HTTPS proxy owns TLS and the login gate. Caller-facing seam: https://<vm>.exe.xyz:<port>/ and the VM's sharing mode. Dependency direction: external-provider. Observable scope: the login redirect and the served page.

Review hosting

Spec review hosting on an exe.dev VM, when its HTTPS proxy is used
ItemContract
ServiceSpec Chat's review server, from a clone on the VM, runs as a systemd user service and restarts after a crash and at boot
ListeningThe VM's internal address on an approved port (7400), which only exe.dev's HTTPS proxy can reach; it never listens on loopback, which the proxy cannot reach
Exposureexe.dev's HTTPS proxy with the VM's sharing mode Private: a request without an exe.dev login is redirected to the login page, so that login is the gate. The exe.dev share port (8000) is not used by Spec Chat
Review URLhttps://<vm>.exe.xyz:7400/<slug>/<spec path>
Registering a specreview-host.py register --slug <spec slug> --owner <session>/<pane> <spec path>, from Spec Chat's review skill, with no exposure argument. A spec has one review row, under its own spec slug, made when it is shaped; lanes link to that row and never register the spec again
Acceptance recordThe review page's Accept hand-off, for the spec at the registered commit; the director's kickoff check octo-feather-accepted reads every session's registry rows and their spools
Spec Chat skillsLinked into each target repository's .agents/skills only, never as .claude/ or .codex/ links (ADR 0001), and never in a home folder; owner chats use them to shape, and the supervisor loads them through externalSkills for spec revisions

Box setup installs the service once with Spec Chat's installer, passing --public <vm>.exe.xyz --service. Spec Chat's word public only means it binds an address other than loopback; exposure stays private because the exe.dev proxy and its login sit in front.

A spec has one review row, under its own spec slug: shaping makes it, acceptance is recorded on it, and a spec revision is reviewed on it. Lanes link to that row and never register the spec under a lane key.

A supervisor sends the owner review links of the form https://<vm>.exe.xyz:7400/<slug>/<spec path>, rewriting the internal link the review service prints until Spec Chat prints the configured public address.

Never make the VM's exe.dev sharing public: a public share has no login and anyone with the link reads the spec.
