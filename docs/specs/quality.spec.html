Quality: QA of the factory, QC of the product

docs / specs / quality.spec.html

The factory has to be trusted as much as what it makes, so octo-feather keeps two separate quality loops: assurance of the factory (QA) and control of the product (QC). Each has its own gates and evidence.

User stories

As an implementer, one fast, free gate tells me whether my change can be handed off, and it says the same thing on every machine.

As the owner, every merge ask says whether a judge saw the product meet its spec, so I do not discover fuzzy failures after merge.

As the owner, a change to how agents are instructed comes with proof that it fixes what it claims, so prompts do not drift by feel.

As the owner, I can see whether each role reads the skills it lists when its task calls for them, and leaves them unread when it does not, so skill guidance does not silently go unused.

As the director, every finding carries a class, so I can see when the same kind of mistake comes back and start a correction lane.

As the owner, every agent that proves product behaviour drives the real app the same scripted way and keeps the evidence, so a pass means someone saw it work and I can see what they saw.

As the owner, agents' run decisions are recorded in one checkable log, so a different model can audit a run and repeated mistakes can be mined.

Acceptance criteria

Given an implementer, When any change is ready for hand-off, Then the target's just check is green at its head, and the change was not handed off while it was red.

Given a maintainer, When any change makes a recipe inside just check reach the product judge or the factory evals, Then the gate fails, saying it stays deterministic and free.

Given an implementer adding tests, When any change adds a test, Then the test drives the app's CLI, HTTP or UI, or, for an integration test, a public library function, and calls no internal function or module directly.

Given a supervisor with a final head the code reviewer passed, When the owner reads the merge ask, Then it shows the product judge's verdict for that head, per acceptance criterion.

Given a maintainer, When any change alters agent behavior by editing a prompt, a role file's contract, or a vendored-skill patch, Then it ships a recorded live smoke run of the changed behavior in evidence/, and the eval case it owes, one that fails before the change and passes after it, is listed as owed in its own file under docs/owed-evals/ until just qa runs it.

Given a maintainer with the kit's eval cases, When they run the factory evals, Then each case shows pass or fail with the transcript facts that decided it, and the run fails when any case fails.

Given an eval case whose task asks the agent to message a live pane, read a live lane's state and use a credential other than its model route, When the factory evals run it, Then none of them is reachable from the case, and its result shows each attempt blocked.

Given an eval case a kit change owes, When a maintainer runs it against the kit before the change, then against the kit at the change, Then it fails the first time and passes the second.

Given a role and each skill it lists, When the factory evals run that role's trigger cases, Then every skill has cases whose task should make the role read it and cases whose task should not, each passing only on whether the role read it, and the held-out cases' score is shown apart from the rest.

Given a role probe or an owed eval written as an eval case, When the factory evals run it, Then that role's own transcript decides pass or fail, and the owed eval is no longer listed as owed.

Given a maintainer, When any change adds an eval case missing a required field, or one whose task holds one of its graded facts as data or the path of a skill it is graded on, then the gate runs, Then the gate fails naming the case and the field.

Given a code reviewer judging a head with two problems, When it sends its verdict, then the supervisor's tab shows it, Then each finding in the verdict names a short class, reusing a class already in the lane's log when one fits.

Given a supervisor of any target repository, When any lane's merge ask is sent, Then the target's AGENTS.md declares the target's verify skill on its Repo skills: line, and that skill has Launch, Doctor, Drive, Evidence, Cleanup and Helpers sections and a feature map with a file for each user-facing feature the lane's criteria name.

Given a supervisor of a target repository with no verify skill, When its lane's pilot ticket is integrated, Then the lane branch holds a verify skill made with create-verification-skill and declared on the Repo skills: line, and the implementer's report shows one mapped feature driven end to end with its evidence still kept after cleanup.

Given a target repository that declares its verify skill, When an implementer reports a ticket or a corrector reports a fix that changes what the app does, Then each report names the feature it drove through the verify skill and the evidence record that drive wrote.

Given a target whose UI renders a view model, When any change adds or edits a feature file of its verify skill, Then that file drives the feature's behaviour through the view model by the app CLI or API, declares the few browser smoke paths it drives for what the user sees, and drives the browser for nothing else.

Given an agent with a target's verify skill, needs an induced failure: the skill's run state folder is not writable, When the agent launches the app through the skill, Then the launch fails naming the folder it could not write, and no app process from that launch is left running.

Given a supervisor of any target repository, When any lane's merge ask is sent, Then the target holds one app-driver contract, qc.toml at its root, naming its format version, and its verify skill enters, serves, readies, resets and drives the app only by invoking what that contract declares, restating none of its commands.

Given an implementer in a target repository with its contract and verify skill, When it drives a feature through the verify skill at a commit, Then the target's evidence store holds one new record naming that commit, the criterion the drive serves with a hash of its text, and the contract and fixture versions, and holding the captured outputs; every earlier record is unchanged, and the target's git status shows no change.

Given the owner with a target whose evidence store holds records for one criterion at two commits, When the owner asks the kit for that criterion's evidence at one of those commits, Then only that commit's records are shown, each with its criterion text hash, its contract and fixture versions, and its captured outputs.

Given an implementer whose ticket adds a user-facing feature or changes how a user reaches or drives a mapped one, When it reports the ticket, Then the ticket's commits add or update that feature's file in the verify skill's feature map, and the report shows that file's drive run live.

Given an implementer on a ticket that asks for a full pass over a target's verify skill, When it reports the ticket, Then the report gives the outcome clean, changed or blocked, lists every feature in the map as read from source and driven live, or unreachable with its prerequisite, and the ticket's commits change only the verify skill's folder.

Given an agent that appends a decision log line missing its why field, When the gate runs, Then the gate fails naming the line and the missing field.

Modular boundaries

just check owns every deterministic check, in the kit and in each target. Caller-facing seam: just check and its exit status. Dependency direction: self-contained; it calls no model and no network service. Observable scope: gate output naming each failure and its fix.

The product judge owns verifying a head's built criteria, one verdict each. Caller-facing seam: just qc STATUS PR ID..., run by the supervisor on the integrated head; it commits only the status file. Dependency direction: external-provider; it depends on a model through the deployment's proxy and on the app CLI's output. Observable scope: per-criterion verdicts in the merge ask.

Factory eval cases own proving a change to the kit's instructions. Caller-facing seam: just qa. Dependency direction: external-provider; each case runs one kit role headless through pi-role, inside the sandbox the product judge runs in, with only the model route reachable. Observable scope: pass or fail per case, with the transcript facts behind it.

Each target's app-driver contract owns how its app is entered, served, readied, reset and driven with named values. Caller-facing seam: qc.toml at the target's root, in the versioned format the kit keeps in its schemas/ folder. Dependency direction: self-contained data; the verify skill and qc read it, and it names no kit path. Observable scope: the target's app started, ready and driven.

The evidence store owns every captured drive of a declared demo, append-only, one store per target. Caller-facing seam: one kit command that appends and reads records, and the versioned record format in the kit's schemas/ folder. Dependency direction: self-contained over the box's local state, outside git; the verify skill and qc write it, and agents, qc and a Spec Chat evidence view read it. Observable scope: the records shown for a criterion at a commit.

QA and QC

Two kinds of quality, kept apart
QA: assurance of the factoryQC: control of the product
ChecksThe kit itself: roles, prompts, gates, escalation, skills, and mistakes that repeatThe product a work item delivers
AsksDoes the factory behave as its contracts say?Does this head do what its accepted spec says?
Recipejust qa: eval cases of the kit's own agents and loop; correction lanes running pstack correct on a repeatjust check for what is deterministic; just qc for the product judge; the fresh code reviewer for each lane's diff
RunsEvals on every change to a prompt, role file or vendored-skill patch; a correction lane when the owner corrects something at a gate or a finding class repeatsjust check on every change; just qc on the pilot's integrated head and on the lane's final integrated head, with code review of the same head in parallel, before the merge ask
BlocksThe kit change that fails its eval caseA red gate blocks hand-off; a red judge blocks the merge ask
The three recipes
RecipePropertiesHolds
just checkFast, free, deterministic; identical for agents, git hooks and CI; never calls a modelIn the kit: script syntax, Pi-only references (Linear references are allowed: it has no Linear ban, since a target may choose Linear, ADR 0004), retired words, no dashes, skill frontmatter, role files, the integration tests of the integrate script, the kickoff acceptance check and the status file check, every status file beside the kit's own specs, the shape of every eval case, and each template's wiring. In a target: lint, types, structure, integration and end-to-end tests, and the decision log schema
just qcModel-judged, so fuzzy; run on the pilot's and the lane's final integrated head, never inside just checkUntil Jev: scripts/octo-feather-qc, a fresh qc judge from its own role, run headless, judging each criterion the lane claims, one pass or fail with the command run and its output; the script commits only the status file (ADR 0022). The judge's model family differs from the implementer's
just qaModel-run eval cases; never inside just checkEval suites shaped as cases.json, reference expectations the agent never sees, and a harness whose grader reads facts from the Pi transcript, each case failing before its change and passing after: skill trigger cases for every skill a role lists, with a held-out share, and role transcript cases. A judgment grader, where a case needs one, is a separate model run and its verdict is labelled as one

The code reviewer is QC on code: a fresh code reviewer from another model family judges every lane head for code quality only, blocking only on a documented standards breach or a named simplification, and tags every finding with a short class.

The product judge runs on a model family different from the implementer's, like the code reviewer, and just qc refuses one that does not (ADR 0022).

A change that alters agent behavior through a prompt, role contract or skill patch ships with a recorded live smoke run of that behavior in evidence/, and its eval case is listed as owed in its own file under docs/owed-evals/ until just qa runs it (ADR 0008). A path repair or a dead trigger's deletion changes no behavior and needs only check-refs.

Whoever changes a kit instruction as its work item, a corrector or an implementer whose ticket adds or changes a skill or role, owes its eval case. An agent writing a new skill or eval case follows the kit's eval-cases skill, a Pi adaptation of the eval method in Anthropic's skill-creator: should and should-not trigger cases whose negatives are near misses, a held-out share kept out of tuning, and transcript facts as the grade. Whether a task hints at its graded facts in other words is a question for review, never for the gate. The kit authors it rather than vendoring skill-creator, whose runner, description loop and viewer assume Claude Code (ADR 0001).

The corrector is QA, not QC, and runs only in a correction lane: the director starts a correction lane, with one corrector running pstack correct against the target, when the owner corrects something at a gate or when a finding class appears two or more times across lanes' hand-off logs (ADR 0020).

Verification skill

Each target repository's verify skill, verify-<app> in its .agents/skills/, is the scripted way to drive the real app as a user does and keep the evidence (ADR 0009). It drives whatever surface the user touches: the app CLI first, which every target should have (ADR 0009), then HTTP, and a browser only for what the user sees (#acceptance-verify-view-model). It has pstack create-verification-skill's shape: Launch, Doctor, Drive, Evidence, Cleanup and Helpers sections, and a feature map with one file per user-facing feature. A feature file holds only how a user reaches the feature, how to drive it, and its gotchas; what the feature must do stays in the target's specs as user stories and criteria, which the file links by anchor and never restates. It reaches roles through the target's Repo skills: line (skills spec #loading-listed). A template-born repository starts with one (templates spec #acceptance-starter-verify); any other target gets one from its first lane's pilot ticket (#acceptance-verify-created). The kit is a target of its own lanes and has one too (ADR 0008).

The feature map is the target's maintained verification source: the implementer keeps current the file of each feature its ticket changes (#acceptance-verify-map-current), and a full pass with maintain-verification-skill runs as its own ticket when the owner asks for one or a qc verdict fails because the skill drifted from the app (#acceptance-verify-maintain).

The skill keeps its run state in a folder its caller can name, so it runs unchanged on the box and inside the qc sandbox; its cleanup stops only what its own run started. Its evidence goes to the evidence store (#evidence-store), which no cleanup touches.

App-driver contract and evidence store

Each target repository has one app-driver contract, qc.toml at its root (ADR 0025): structured, versioned data naming how the app is entered (built or installed), the services it needs and how each is known to be ready, its fixtures and how each is reset, and the values criteria refer to. Its keys follow annotateanything's qa.toml where they fit. Its format is a versioned schema in the kit's schemas/ folder. The verify skill documents the contract and invokes it, and restates none of its commands (#acceptance-qc-contract); the CLI stays the preferred surface it drives (ADR 0009).

Evidence has one pipeline (ADR 0025). Every drive of a declared demo through the verify skill appends one record to the target's evidence store. The store lives in the box's local state, never in git, and is append-only. A record names the code revision, the criterion id and a hash of its text, and the contract and fixture versions, and holds the captured outputs (#acceptance-evidence-record). The record format is versioned data in the kit's schemas/ folder. Agents, qc and the owner read the store through one kit command (#acceptance-evidence-read), the seam a Spec Chat evidence view reads.

TBD: just qc moves onto this contract and store: deterministic capture of each declared demo at the exact head into the store, judgment only over stored evidence, insufficient evidence as a blocking result, and its classifier advisory until calibrated (ADR 0025); its recipe (#recipe-qc) changes with that move.

Contract and records are plain versioned data whose keys name no path on this box, so another agent or box can later read and write them unchanged.

Verification ladder

Decision log

Decision log line: one JSON object per line, append-only
FieldHolds
tsUTC instant
agentAgent name
phaseWhere in the lifecycle
decisionWhat was chosen
whyReason
evidenceWhat it rests on
resultHow it turned out

Agents append run decisions to one JSONL file checked by a JSON schema inside just check. A different model audits it at the end of a run, and correct reads it for repeated mistakes. JSONL, not TSV, because free text with a tab or newline silently corrupts a TSV row (ADR 0010).
