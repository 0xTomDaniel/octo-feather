Quality: QA of the factory, QC of the product

docs / specs / quality.spec.html

The factory has to be trusted as much as what it makes, so octo-feather keeps two separate quality loops: assurance of the factory (QA) and control of the product (QC). Each has its own gates and evidence.

User stories

As an implementer, one fast, free check tells me whether my change can be handed off inside a lane, and the full gate it is part of says the same thing on every machine.

As the owner, every merge ask says whether a judge saw the product meet its spec, so I do not discover fuzzy failures after merge.

As the owner, a change to how agents are instructed comes with proof that it fixes what it claims, so prompts do not drift by feel.

As the owner, a change to a skill's or a role's wording is measured over repeated runs beside the wording before it, with its cost, so wording is tuned on evidence, not on one lucky run.

As the owner, I can see whether each role reads the skills it lists when its task calls for them, and leaves them unread when it does not, so skill guidance does not silently go unused.

As the director, every finding carries a class, so I can see when the same kind of mistake comes back and start a correction lane.

As the owner, every agent that proves product behaviour drives the real app the same scripted way and keeps the evidence, so a pass means someone saw it work and I can see what they saw.

As the owner, each criterion's verdict comes from evidence a deterministic capture recorded at the judged head, so the same evidence always gets the same verdict and I can see what it was judged from.

As the owner, each built criterion names the evidence and tests that enforce it and shows stale once its code or its text changes, so drift between spec and code is visible.

As the owner, agents' run decisions are recorded in one checkable log, so a different model can audit a run and repeated mistakes can be mined.

As the owner, every target checks the data crossing its public edges with its language's schema library, so malformed or unexpected data fails at the edge, named, instead of deep inside the product.

Acceptance criteria

Given an implementer, When any change is ready for hand-off, Then the target's fast tier, just fast, is green at its head, or just check where the target has no fast tier, and the change was not handed off while it was red.

Given an implementer in the kit whose change touches one script, When it runs just fast, Then the static checks run, then the tests whose recorded coverage reaches that script and every test with no recorded coverage, none of them end-to-end, and the output names each test it chose and why.

Given a maintainer, When any change makes a recipe inside just check reach the product judge or the factory evals, Then the gate fails, saying it stays deterministic and free.

Given an implementer adding tests, When any change adds a test, Then an end-to-end test drives a public interface the product offers its users (its CLI, HTTP, UI, MCP or another public protocol), and an integration test drives the interface of a deep module with a stable interface, public or internal, at a seam written down from the ticket's acceptance criteria before any test, and never a private helper or a shallow wrapper whose interface mirrors its implementation.

Given an implementer in any target repository, When any change reads structured data from outside the product (a CLI, HTTP or MCP payload, a provider or API response, config, a persisted file) or writes data another tool reads, Then the data is parsed with a real parser and validated once at the edge by the repository's schema library into strict typed models that reject unknown fields, trusted inside, and written out only from typed models; a hand-written shape check stands only where its reason is stated where it lives.

Given a maintainer of the kit on the factory's machine, When the full gate runs at a head of main, then the fast tier runs for a change to one script, Then the full gate finishes in under five minutes and the fast tier in under ninety seconds.

Given a maintainer of the kit, When the gate runs its tests, Then the run shows and records each test's CPU time, the time used by the test and every process it started, and names each integration test over the per-test CPU budget with its CPU time and the budget.

Given an implementer in the kit, When it adds or changes an integration test that uses more CPU time than the per-test CPU budget, then runs the gate, Then the gate fails, naming that test, its CPU time and the budget, and an end-to-end test is never held to the budget.

Given a supervisor with a final head the code reviewer passed, When the owner reads the merge ask, Then it shows the product judge's verdict for that head, per acceptance criterion.

Given a maintainer, When any change alters agent behavior by editing a prompt, a role file's contract, or a vendored-skill patch, Then it ships a recorded live smoke run of the changed behavior in evidence/, and the eval case it owes, one that fails before the change and passes after it, is listed as owed in its own file under docs/owed-evals/ until just qa runs it.

Given a maintainer with the kit's eval cases, When they run the factory evals, Then each case shows pass or fail with the transcript facts that decided it, and the run fails when any case fails.

Given an eval case whose task asks the agent to message a live pane, read a live lane's state and use a credential other than its model route, When the factory evals run it, Then none of them is reachable from the case, and its result shows each attempt blocked.

Given an eval case a kit change owes, When a maintainer runs it against the kit before the change, then against the kit at the change, Then it fails the first time and passes the second.

Given a role and each skill it lists, When the factory evals run that role's trigger cases, Then every skill has cases whose task should make the role read it and cases whose task should not, each passing only on whether the role read it, and the held-out cases' score is shown apart from the rest.

Given a maintainer with an eval case its role passes on some runs and fails on others, When they run the factory evals with several runs of that case, Then the case shows how many of its runs passed out of how many, with the spread of its results, and it passes only when every run passed.

Given a maintainer, When they run the factory evals with several runs of a case, Then the case shows the time and the tokens its runs took, each as a mean with its spread.

Given a maintainer with a kit change and the kit before it, When they run the factory evals comparing the two, Then each case shows its pass rate, time and tokens on the kit before beside the kit at the change, with the difference, from runs made in the same evaluation.

Given a comparison of two kits in which one case passes on both, one fact holds on both in a case whose result differs, one case passes on some runs only, and one case passes as often on both but takes longer at the change, When the maintainer reads the comparison's analysis, Then it flags the first case and that fact as not discriminating, the third case as high variance and the fourth as a cost tradeoff, and no model decided any flag.

Given an eval case whose outcome no transcript fact can grade, When the factory evals run it, then a maintainer records a verdict and a note on its output, Then the case shows awaiting review with its output until the verdict is recorded, then shows the verdict and the note, and the next run of that case shows them beside its new output.

Given an incident the owner or a live run caught, When a maintainer writes its eval case on the real repository at the commit the incident happened on, then runs it against the kit before the fix, then at the fix, Then the role works on that repository at its full size, and the case fails the first time and passes the second.

Given a maintainer agent changing a skill's wording with the kit's eval-cases skill, When it proves the change, Then the proof it records shows the case's pass rate over repeated runs on the kit before beside the kit at the change.

Given a role probe or an owed eval written as an eval case, When the factory evals run it, Then that role's own transcript decides pass or fail, and the owed eval is no longer listed as owed.

Given a maintainer, When any change adds an eval case missing a required field, or one whose task holds one of its graded facts as data or the path of a skill it is graded on, then the gate runs, Then the gate fails naming the case and the field.

Given a code reviewer judging a head with two problems, When it sends its verdict, then the supervisor's tab shows it, Then each finding in the verdict names a short class, reusing a class already in the lane's log when one fits.

Given a supervisor of any target repository, When any lane's merge ask is sent, Then the target's AGENTS.md declares the target's verify skill on its Repo skills: line, and that skill has Launch, Doctor, Drive, Evidence, Cleanup and Helpers sections and a feature map with a file for each user-facing feature the lane's criteria name.

Given a supervisor of a target repository with no verify skill, When its lane's pilot ticket is integrated, Then the lane branch holds a verify skill made with create-verification-skill and declared on the Repo skills: line, and the implementer's report shows one mapped feature driven end to end with its evidence still kept after cleanup.

Given a target repository that declares its verify skill, When an implementer reports a ticket or a corrector reports a fix that changes what the app does, Then each report names the feature it drove through the verify skill and the evidence record that drive wrote.

Given a target whose UI renders a view model, When any change adds or edits a feature file of its verify skill, Then that file drives the feature's behaviour through the view model by the app CLI or API, declares the few browser smoke paths it drives for what the user sees, and drives the browser for nothing else.

Given an agent with a target's verify skill, needs an induced failure: the skill's run state folder is not writable, When the agent launches the app through the skill, Then the launch fails naming the folder it could not write, and no app process from that launch is left running.

Given a supervisor of any target repository, When any lane's merge ask is sent, Then the target holds one app-driver contract, qc.toml at its root, naming its format version, and its verify skill enters, serves, readies, resets and drives the app only by invoking what that contract declares, restating none of its commands.

Given an implementer in a target repository with its contract and verify skill, When it drives a feature through the verify skill at a commit, Then the target's evidence store holds one new record naming that commit, the criterion the drive serves with a hash of its text, and the contract and fixture versions, and holding the captured outputs; every earlier record is unchanged, and the target's git status shows no change.

Given the owner with a target whose evidence store holds records for one criterion at two commits, When the owner asks the kit for that criterion's evidence at one of those commits, Then only that commit's records are shown, each with its criterion text hash, its contract and fixture versions, and its captured outputs.

Given an implementer whose ticket adds a user-facing feature or changes how a user reaches or drives a mapped one, When it reports the ticket, Then the ticket's commits add or update that feature's file in the verify skill's feature map, and the report shows that file's drive run live.

Given an implementer on a ticket that asks for a full pass over a target's verify skill, When it reports the ticket, Then the report gives the outcome clean, changed or blocked, lists every feature in the map as read from source and driven live, or unreachable with its prerequisite, and the ticket's commits change only the verify skill's folder.

Given a supervisor whose lane claims a criterion its target's app-driver contract declares a demo for, When it runs just qc on the lane's integrated head, Then the target's evidence store holds a new record for that criterion at that head, holding the demo's command, exit status and output, its criterion text hash and the contract and fixture versions, and the qc report names that record.

Given a supervisor whose lane claims a criterion one tagged acceptance test covers, When it runs the full gate on the lane's final head, then runs just qc on that head, Then the evidence store holds one record of that test's run from the gate, naming each case it selected and that case's outcome, and the qc report judges the criterion from that record, the test having run once.

Given a supervisor whose lane claims a criterion whose tagged acceptance test was skipped in the final head's full gate, When it runs just qc on that head, Then that criterion's result is insufficient evidence naming the skipped case, and no agent judge runs for it.

Given a code reviewer judging a lane head that claims a criterion through a tagged acceptance test, When it sends its verdict, then the supervisor's tab shows it, Then the verdict says whether that test's assertions and substitutions demonstrate the criterion, naming the test.

Given a code reviewer judging a head whose diff extends a piece of hand-built infrastructure the kit already has, and whose writer's report gives no prior art line for it, When it sends its verdict, then the supervisor's tab shows it, Then the verdict blocks the head as a reinvented library until the writer's report says whether a maintained, pinned tool now does that job, as it would for new infrastructure.

Given a code reviewer judging a head whose diff, in product code or a test, reads structured data from outside the product without validating it at the edge, or with a hand-written shape check whose reason is not stated, When it sends its verdict, then the supervisor's tab shows it, Then the verdict blocks the head as an unvalidated edge, naming the edge and the schema library to use.

Given a supervisor whose lane claims a criterion its target's app-driver contract declares a browser demo for, When it runs just qc on the lane's integrated head, Then that criterion's new evidence record holds the screenshots the demo took in a headless browser inside the qc sandbox.

Given a supervisor whose lane claims two criteria with declared demos, one whose demo's checks pass and one whose demo's checks fail, When it runs just qc on the same head twice, Then both reports give the first criterion pass and the second fail, each with evidence state complete and decision source the demo's checks.

Given a supervisor whose lane claims a criterion whose demo's checks pass, needs an induced failure: the kit's judgment model answers that the evidence does not show the criterion, When it runs just qc on the lane's integrated head, Then the criterion passes, and the qc report shows the model's answer and confidence beside it, labelled as an advisory model judgment.

Given a supervisor whose lane claims a criterion with a declared demo, needs an induced failure: a step the demo needs cannot run in the qc sandbox, When it runs just qc on the lane's integrated head, then checks its merge ask, Then the qc report shows that criterion as insufficient evidence, naming what is missing, the criterion stays planned, and the merge ask check fails naming it.

Given a supervisor whose lane claims a criterion its target's app-driver contract declares no demo for, When it runs just qc on the lane's integrated head, Then that criterion's result comes from a fresh agent judge with a fixed time cap, labelled agent fallback in the qc report and in the merge ask, and the judge's report is stored as that criterion's evidence record.

Given a supervisor whose lane claims a criterion its app-driver contract proves by named cases of stored factory eval runs, When it runs just qc on two heads whose role, skill and case files equal the runs' kit, Then both reports give it the same result, decision source the demo's checks read from the runs' stored grading, and at a head where one of those files differs the result is insufficient evidence naming that file.

Given a supervisor whose lane claims a criterion, When it runs just qc on the lane's integrated head, Then the criterion's demo or judge runs inside a maintained, pinned agent sandbox the kit configures, the kit adding only the isolation that sandbox cannot give, each such step stating why where it lives, and every escape the qc tests try still fails: a mask removed, a credential copied out, a write to the worktree kept, a process left running, a live Herdr session reached.

Given a maintainer of the kit on the factory's machine, When a judge command that does nothing runs in the qc sandbox, one run after another, Then each run reports CPU time for sandbox setup, proof and cleanup, with every process they start, and whether it meets the 0.8-second optimization target; exceeding that target alone does not fail a run whose functional, proof, cleanup and complete-accounting checks pass.

Given a supervisor whose lane's earlier head passed two criteria in just qc, When a merge of main changes a path only one of them covers, then the supervisor runs just qc on the new head naming both, Then the qc report judges that one again at the new head and shows the other carried, naming the head it was judged at and its record, and both read built in the status file.

Given a supervisor whose just qc run passed a criterion, When the owner reads that spec's status file at the head the run left, Then the criterion is built with the lane's pull request and names the evidence record it was judged from, the commit that evidence was captured at, and the tests tagged with it or its demo's.

Given the owner with a spec holding two built criteria, When a later commit changes the code one of them was judged on, then the owner asks the kit for that spec's criterion status, Then that criterion shows stale, naming the commit its evidence was captured at and the change that made it stale, and the other shows current.

Given an agent that appends a decision log line missing its why field, When the gate runs, Then the gate fails naming the line and the missing field.

Modular boundaries

just check owns every deterministic check, in the kit and in each target, and just fast runs the part of it a change can affect. Caller-facing seam: just check, the full tier, and just fast, the fast tier, and their exit status. Dependency direction: self-contained; it calls no model and no network service. Observable scope: gate output naming each failure and its fix.

The qc capture owns running each claimed criterion's tagged acceptance tests once inside the final head's full gate, or its declared demo, at the exact head in the qc sandbox, and storing what it captured; it calls no model and decides nothing. Caller-facing seam: the final head's full gate and the first step of just qc STATUS PR ID...; its output is evidence records. Dependency direction: self-contained over the target's app-driver contract, the qc sandbox and the evidence store; it calls no model. Observable scope: one new record per criterion with a declared demo, at that head.

The product judge owns one result per claimed criterion, pass, fail or insufficient evidence, judged only from stored evidence. Caller-facing seam: just qc STATUS... PR ID..., run by the supervisor on the integrated head; it commits only the status files of the specs it names, in one commit. Dependency direction: external-provider; it depends on the evidence store, and on a model only for the kit's judgment model and the agent fallback, both through Pi. Observable scope: per-criterion results in the qc report and the merge ask.

Factory eval cases own proving a change to the kit's instructions. Caller-facing seam: just qa. Dependency direction: external-provider; each case runs one kit role headless through pi-role, inside the sandbox the product judge runs in, with only the model route reachable. Observable scope: pass or fail per case, with the transcript facts behind it, its pass rate, time and tokens over repeated runs, beside a baseline kit's when compared, and the analysis of that comparison.

Each target's app-driver contract owns how its app is entered, served, readied, reset and driven with named values. Caller-facing seam: qc.toml at the target's root, in the versioned format the kit keeps in its schemas/ folder. Dependency direction: self-contained data; the verify skill and qc read it, and it names no kit path. Observable scope: the target's app started, ready and driven.

The evidence store owns every captured drive of a declared demo, append-only, one store per target. Caller-facing seam: one kit command that appends and reads records, and the versioned record format in the kit's schemas/ folder. Dependency direction: self-contained over the box's local state, outside git; the verify skill and qc write it, and agents, qc and a Spec Chat evidence view read it. Observable scope: the records shown for a criterion at a commit.

QA and QC

Two kinds of quality, kept apart
QA: assurance of the factoryQC: control of the product
ChecksThe kit itself: roles, prompts, gates, escalation, skills, and mistakes that repeatThe product a work item delivers
AsksDoes the factory behave as its contracts say?Does this head do what its accepted spec says?
Recipejust qa: eval cases of the kit's own agents and loop; correction lanes running pstack correct on a repeatjust check for what is deterministic; just qc for the product judge; the fresh code reviewer for each lane's diff
RunsEvals on every change to a prompt, role file or vendored-skill patch; a correction lane on the triggers issue-lifecycle #lanes-correction ownsjust check on every change; just qc on the pilot's integrated head and on the lane's final integrated head, with code review of the same head in parallel, before the merge ask
BlocksThe kit change that fails its eval caseA red gate blocks hand-off; a red judge blocks the merge ask

Each case can run several times, with its pass rate, spread, time and tokens, beside a baseline kit's in the same evaluation, followed by a deterministic analysis of the comparison; a case no fact can grade waits for a maintainer's recorded verdict. A judgment grader, where a case needs one, is a separate model run and its verdict is labelled as one

A test, in the kit or a target, is end-to-end only when its purpose is a real external system working (a real install, the qc sandbox's escape checks, real Herdr, a real shaping session, and the like) or when it is live, waits on the wall clock, drives a browser or reaches a deployed system; it is marked as one and runs only in the full tier, never in the fast tier. Every other test is an integration test: it drives a seam #acceptance-public-surfaces allows, with stand-ins only at external boundaries, for what is slow or external (the codebase-design skill's dependency categories). When no deep module with a stable interface exists at the seam a criterion needs, the implementer refactors product code to create one as its own step: it pins current behavior first, deepens the module, then writes the tests at the new interface. Product code for a real deep interface is no test leak; a test-only flag, hook or branch still is. A kit integration test stays within the per-test CPU budget (#acceptance-test-cpu-budget), measured in CPU time so machine load does not move it. The budget is set from measured CPU times once repeated runs show them stable. When the gate misses a time target, the fix starts from measurement: the slowest items and what they spend their time on, then small fixes in the tests and the runner; caching or a task runner is proposed only with measured evidence that it closes the gap. How a test stands in for what it does not own, replays a recording and shares its support: the tdd skill's mocking guide. A template's tests follow templates #templates-tests-rule.

The code reviewer is QC on code: a fresh independent code reviewer from another model family judges every lane head for code quality, and, for each criterion the lane claims through a tagged acceptance test, whether the selected tests, assertions, expected values and substitutions demonstrate that criterion (#acceptance-review-test-adequacy); it blocks only on a documented standards breach, a test that does not demonstrate its criterion being one, or a named simplification, and tags every finding with a short class. For the owner-authorized sandbox (including its owned-process inspection product-gap follow-up), light-test, revision-repair and final-cleanup lanes of this sprint only, fresh independent GPT-only reviewer sessions may share the writer's model family; this exception expires at the sprint pause after final cleanup. The lane's call log and merge ask record the owner-delegated authority and actual invoked models, never role defaults. Writer and reviewer use separate sessions and a new verdict is required, never a relabelled blocked report. Outside this bounded exception the different-family rule is unchanged.

The agent fallback follows the eligibility policy owned by quality-reviewer (ADR 0022).

A change that alters agent behavior through a prompt, role contract or skill patch ships with a recorded live smoke run of that behavior in evidence/, and its eval case is listed as owed in its own file under docs/owed-evals/ until just qa runs it (ADR 0008). A path repair or a dead trigger's deletion changes no behavior and needs only check-refs.

Whoever changes a kit instruction as its work item, a corrector or an implementer whose ticket adds or changes a skill or role, owes its eval case. An agent writing a new skill or eval case follows the kit's eval-cases skill, a Pi adaptation of the eval method in Anthropic's skill-creator: should and should-not trigger cases whose negatives are near misses, a held-out share kept out of tuning, transcript facts as the grade, each fact reading the outcome the role produced rather than a proxy for it, repeated runs beside a baseline kit as the measure, and owner-caught or live-caught incidents replayed on their real repository as regression cases. The skill owns how a case measures; writing-for-agents owns how the instruction under test is written. Whether a task hints at its graded facts in other words is a question for review, never for the gate. The kit authors it rather than vendoring skill-creator, whose runner, description loop and viewer assume Claude Code (ADR 0001).

The corrector is QA, not QC, and runs only in a correction lane: the director starts a correction lane, with one corrector running pstack correct against the target, on the triggers issue-lifecycle #lanes-correction owns (ADR 0020).

Verification skill

Each target repository's verify skill, verify-<app> in its .agents/skills/, is the scripted way to drive the real app as a user does and keep the evidence (ADR 0009). It drives whatever surface the user touches: the app CLI first, which every target should have (ADR 0009), then HTTP, and a browser only for what the user sees (#acceptance-verify-view-model). It has pstack create-verification-skill's shape: Launch, Doctor, Drive, Evidence, Cleanup and Helpers sections, and a feature map with one file per user-facing feature. A feature file holds only how a user reaches the feature, how to drive it, and its gotchas; what the feature must do stays in the target's specs as user stories and criteria, which the file links by anchor and never restates. It reaches roles through the target's Repo skills: line (skills spec #loading-listed). A template-born repository starts with one (templates spec #acceptance-starter-verify); any other target gets one from its first lane's pilot ticket (#acceptance-verify-created). The kit is a target of its own lanes and has one too (ADR 0008).

The feature map is the target's maintained verification source: the implementer keeps current the file of each feature its ticket changes (#acceptance-verify-map-current), and a full pass with maintain-verification-skill runs as its own ticket when the owner asks for one or a qc verdict fails because the skill drifted from the app (#acceptance-verify-maintain).

The skill keeps its run state in a folder its caller can name, so it runs unchanged on the box and inside the qc sandbox; its cleanup stops only what its own run started. Its evidence goes to the evidence store (#evidence-store), which no cleanup touches.

App-driver contract and evidence store

Each target repository has one app-driver contract, qc.toml at its root (ADR 0025): structured, versioned data naming how the app is entered (built or installed), the services it needs and how each is known to be ready, its fixtures and how each is reset, the values criteria refer to, and, per criterion, the code paths it covers, its fixtures, whether it needs a headless browser, the artifacts it must leave, and a demo command only for a criterion no tagged test covers, for one a factory eval proves a command reading the stored eval runs it names (#qc-fallback); which tests enforce a criterion is the tag on each test, never a list in the contract. Its keys follow annotateanything's qa.toml where they fit. Its format is a versioned schema in the kit's schemas/ folder. The verify skill documents the contract and invokes it, and restates none of its commands (#acceptance-qc-contract); the CLI stays the preferred surface it drives (ADR 0009).

Evidence has one pipeline (ADR 0025). Every drive of a declared demo through the verify skill appends one record to the target's evidence store. The store lives in the box's local state, never in git, and is append-only. A record names the code revision, the criterion id and a hash of its text, and the contract and fixture versions, and holds the captured outputs (#acceptance-evidence-record). The record format is versioned data in the kit's schemas/ folder. Agents, qc and the owner read the store through one kit command (#acceptance-evidence-read), the seam a Spec Chat evidence view reads.

Contract and records are plain versioned data whose keys name no path on this box, so another agent or box can later read and write them unchanged.

How just qc judges

Capture comes first, calls no model and decides nothing. A criterion's acceptance test is an ordinary test of the suite tagged with its criterion id through the test runner's own mechanism; a criterion may have several, and one test may serve several criteria, and nothing caps how many a flow has. The tag says what a test proves, never how heavy it is: an acceptance test's kind and weight follow #test-kinds like any other test's. The final head's full gate runs each tagged test once, through the qc capture in the qc sandbox (ADR 0022), the capture arranged before the run, and that one execution counts both toward the full gate and as the criterion's record in the evidence store (#evidence-store): the head and a clean worktree, the criterion text hash, the contract, fixture and gate configuration versions, the cases it selected, the command, each case's outcome, the output, any screenshots and the paths it covers (#acceptance-one-execution). Untagged tests run as before. For a claimed criterion no tagged test covers, just qc runs the demo its contract declares at the exact integrated head in the qc sandbox, in a headless browser there when the demo declares one, and appends what it captured to the evidence store: the command, exit status, output and any screenshots, under the record's revision, criterion text hash and contract and fixture versions (#acceptance-qc-capture). A run judges only records captured at that head and never reruns a valid one; a carried result: carry. CI stays a separate full run, and the pilot and every other checkpoint capture their own execution.

Judgment reads only the store. A criterion's evidence state is complete when its record is from the judged head with a clean worktree, its criterion text hash matches the spec, and the demo ran to its end with every output it declares; otherwise it is incomplete, naming what is missing. A tagged test's record is complete only when every case it selects ran to its end with an outcome: a skipped, missing, timed-out or partial case leaves it incomplete, and a declared test that is broken never falls back to the agent judge (#acceptance-one-execution-incomplete). Complete evidence is judged first by exact assertions: the tagged test's own assertions, a completed assertion failure being a fail, or the demo's own checks, which its exit status reports. Except under the explicit bounded sprint authorization, the kit's judgment model then gets one closed question, whether this evidence shows this criterion, given the criterion's text and the record's outputs (judgment spec, #question-criterion-evidence). Its answer is advisory (judgment #rule-advisory): it is shown beside the result, labelled as a model judgment, and no gate reads it; a result comes only from the demo's checks or the labelled agent fallback. The named owner-delegated authorization gpt-only-sprint-2026-11-08 temporarily suspends only this non-gating classifier advice for declared-demo QC in the owner-authorized current-sprint sandbox (including its owned-process inspection product-gap follow-up), light-test, revision-repair and final-cleanup lanes. It expires at the sprint pause after final cleanup. Each use is explicit: the report says advisory NOT RUN under that named authorization, its scope and expiry, with no model answer or confidence fabricated and no claim the classifier was unavailable. Real demo execution, evidence completeness, deterministic checks, QC outcomes and status writes remain mandatory and unchanged. A model-fallback criterion still requires its fresh independent GPT judge; this suspension does not substitute for it. The canonical judgment model and the default advice path outside this exception are unchanged; no substitute classifier or rebench is implied.

Each claimed criterion gets one result, pass, fail or insufficient evidence, with its evidence state, its decision source (the demo's checks or the agent fallback), the judgment model's advisory answer or the explicit authorized NOT RUN state from the bounded sprint exception, the record it was judged from and the judged head. Insufficient evidence is a result, never a failure to triage: the criterion stays planned and the merge ask check fails until a rerun gives it pass or fail (#acceptance-qc-insufficient). The script, never a model, writes the status file: each passed criterion built with the lane's pull request, its record, the commit that record was captured at, and the tests its demo declares (#acceptance-built-links).

Only a criterion with neither a tagged acceptance test nor a declared demo gets the agent fallback: a fresh qc judge from its own role, in the same sandbox, with a fixed time cap, judging that criterion alone. Its report is stored as the criterion's evidence record, and its result is labelled agent fallback in the qc report and the merge ask (#acceptance-qc-fallback). Tagging a test or declaring a demo is how a criterion leaves the fallback. A criterion a factory eval proves (just qa, a model run the qc sandbox cannot repeat) leaves it the same way: its demo names the stored eval runs and cases that prove it, and its result is the grading those runs stored, read in the qc sandbox, never a judge reading their records as prose: pass when every named case passed in every run, fail when one failed. The same runs give the same result at every head whose role, skill, case and fixture files equal the kit the runs ran; at a head where one differs, or with a named run missing, the result is insufficient evidence naming it, so a change to those files, a merge of main included, needs the evals run again and the demo's runs renamed (#acceptance-qc-eval-verdict). Its evidence in the repository names the runs, never a copy of them.

A built criterion's evidence goes stale when the criterion's text changes, when a code path its demo declares it covers changes after the commit its evidence was captured at, or when a test it names is gone. octo-feather-spec-status shows each built criterion current or stale with what made it stale, the drift detector between spec and code (#acceptance-evidence-stale); a stale criterion stays built until a lane's just qc judges it again.

After a lane's head changes, above all by a merge of main, just qc on the new head carries each named criterion that passed at an earlier head of the same lane the new head contains, when its evidence is still current at the new head by the stale rule read from its record: its text unchanged, no path its evidence covers and no test it names changed between the two heads, and no test newly tagged with it at the new head, and the contract, fixture and gate configuration versions its record names unchanged. A carried criterion keeps that pass, its record and its decision source, is neither captured nor judged again, and the qc report shows it carried, naming the head it was judged at and its record. Every other named criterion is judged at the new head as before. What moved is exact, read from each record's own paths, never guessed: a criterion with no covered path, such as one the agent fallback judged, and one that failed or had insufficient evidence are never carried (#acceptance-qc-carry).

Only a change to a path its demo declares it covers makes a built criterion's evidence stale for a code change; an unrelated code change leaves that criterion's evidence current.

Verification ladder

Data at public edges

How each language meets the edge rule is its language skill's practice (python, typescript), with that language's established schema library; a repository with none starts on the one its template ships (templates spec #templates-table). Data the repository writes for itself, a test's checked-in fixture or the literal a test compares output to, is not from outside the product; data another tool writes, which a test reads, is.

The kit's own scripts stay standard-library-only (AGENTS.md Rules), the stated reason for their hand-written checks: each parses with a standard-library parser (JSON, TOML, arguments), never a regular expression over a structured format, and validates the result once at its edge into a typed record, failing with the field it rejects.
