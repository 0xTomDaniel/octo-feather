Roles, role files and launch

docs / specs / roles.spec.html

Every role is one file in agents/: frontmatter that scripts/pi-role turns into Pi flags and a body that is its contract. A reusable general-purpose worker executes finite tasks for a director or supervisor; no separate launch mode is needed for each kind of task. Every agent is Pi, started through herdr-spawn and scripts/pi-role (ADR 0016). Meanings of the role names are in GLOSSARY.md.

User stories

As the owner, a role runs with the same model, tools and skills whether it is in a tab or headless, so a role behaves the same wherever it runs.

As the owner, the code reviewer is never from the same model family as the implementer, so one family's blind spots do not pass their own review.

As the owner, the director has no edit or write tool and its contract forbids editing code, so the agent holding the whole picture never gets pulled into doing the work.

As the owner, every agent can run several tool calls in one script and keep large results out of its context, without reaching any tool its role file does not list, so agents work faster and cheaper with the same limits.

As the owner, the agents that direct, build, fix, review and shape can search the web and read pages, so they find a maintained library or the current docs before writing code or a spec themselves.

As the owner, my director is accountable for keeping the whole factory delivering: it delegates substantive investigation and execution to reusable general workers or the responsible lane supervisor, keeps coordination and decisions, unblocks without me, and brings me only spec acceptance, merge approval, owner-held access and consequential product or risk decisions.

As the owner watching the factory, each lane has its own workspace with its supervisor and workers, and the director has its own.

As the owner, the reflector is a fresh agent of another model family than the director and supervisors whose work it reads, with no tool that changes a file, so its findings come from what happened and not from the agents it judges.

As the owner, I shape a spec with the shaper, an agent that reads each shaping skill when its step comes, so every shaping runs the same method whether I start it or the director starts it for me.

As a maintainer, a role file the launcher cannot honour fails the gate before any agent starts with it.

As the owner, no agent's git stash can take or drop another agent's work in a repository whose lanes and workers share it through worktrees, so a lane never loses work to another.

Acceptance criteria

Given a maintainer, When a code reviewer is started in a worker tab, then one is run headless on the same head, Then both reviewers report the same model, thinking level, tools and skills, and both have loaded the target repository's AGENTS.md.

Given a maintainer, When any change sets the code reviewer's model to the implementer's model family, Then the gate fails, saying the reviewer must use a different family.

Given a maintainer, When any change adds a frontmatter key the launcher does not honour to a role file, Then the gate fails naming the file and the key.

Given a maintainer, When any change lists a skill in a role file that the kit does not hold, Then the gate fails naming the file and the skill.

Given a maintainer, When any change sets a role's model to one outside the allowed list, Then the gate fails naming the file and the model.

Given a box whose global Pi skill folder holds skills no role file lists, When the supervisor starts an implementer, Then the implementer has exactly the skills its role file lists available and none of the global ones.

Given the owner, When the owner starts the director through pi-role, in a tab or headless (herdr-spawn --role builds the same pi-role launch, ADR 0016), Then the director's tools are read, grep, find, ls, bash, codemode and the web tools, with no edit or write tool, and a codemode script the director runs can call no edit or write tool either.

Given a maintainer, When each role is started, the director, supervisor, general worker, implementer, corrector and code reviewer in a tab and the code reviewer headless, Then each one's tools are its role file's tools plus codemode, and a codemode script it runs can call exactly its role file's tools.

Given a maintainer, When a reflection starts its reflector, Then the reflector reports a model of another family than the director's and the supervisor's, at high thinking, with read, grep, find and ls as its only tools besides codemode, and no edit, write or bash tool.

Given the owner in a target repository with Spec Chat's skills installed in it and other skills in the owner's home folder, When the owner starts the shaper with just shape, Then the shaper runs through pi-role with its role file's model, thinking and tools and exactly the skills its role file lists, Spec Chat's from the target repository and none from the home folder.

Given the owner in a target repository with Spec Chat's skills installed in it, whose existing specs and ADRs do not meet Spec Chat's shaping contract, When the owner asks the shaper for a change there, Then the shaper offers the owner a repair of those specs and ADRs to that contract before it writes the change's spec.

Given a box with no web search key set anywhere, When each role, the director, supervisor, general worker, implementer, corrector and code reviewer, is started through pi-role, in a tab or headless (herdr-spawn --role builds the same pi-role launch, ADR 0016), Then the director, general worker, implementer, corrector and code reviewer each have web search and page fetch from both Parallel and Exa, and a search one of them runs returns results, while the supervisor has no web tool.

Given a box whose user Pi configuration and a target repository each name another MCP server, When a supervisor starts an implementer in that target (through pi-role), Then the implementer has the web tools and no tool from that other server, and a supervisor started there has no MCP tool at all.

Given a maintainer, When a change adds a server to the kit's web server list and changes no role file, Then every role that lists the web tools has that server's tools at its next start, and no other role has them.

Given a supervisor with a fixture to be added containing two finished worker results within its lane scope, When the supervisor integrates those results then prepares its merge ask, Then the supervisor owns the single lane PR and its verification evidence, and the PR awaits the owner's merge decision without a routine director permission gate.

Given a supervisor with a fixture to be added containing a closed implementation assignment and independent ready work within actual resource limits, When the supervisor assigns the independent work, Then its worker has a different provider-session identity from the closed assignment and a self-contained task brief.

Given a director with a fixture to be added containing authorized shared maintenance and an available product-worktree-only implementer, When the director delegates that task, Then the general worker receives the scoped maintenance brief and the product implementer receives no host-write assignment.

Given a director with a fixture to be added containing independent research and maintenance tasks within existing authority and actual resource limits, When the director assigns both tasks, Then two distinct fresh provider-session identities use the same general-worker role contract with different task briefs and the director as parent, without a task-specific launch mode.

Given a general worker with a fixture to be added containing a reachable parent and a peer lane, When the worker attempts to send to the peer then sends its result to its parent, Then the peer receives no message and the parent receives the result.

Given a general worker with a fixture to be added containing a candidate inside its task scope named by an existing parked-worker record, When the worker performs its authorized host operation, Then the protected candidate remains intact and the result identifies its protection.

Given a general worker with a fixture to be added containing proven disposable kit scratch inside authorized roots and a director-authorized candidate class, with no protecting record or live use, When the worker performs its removal task, Then eligible scratch is removed and the parent receives itemized removed-candidate sizes and separately measured free-space change, without unsupported reclaimed-byte credit or another routine Go.

Given a general worker with a fixture to be added containing disposable scratch outside its assigned roots, When the worker performs its authorized host operation, Then that scratch remains intact and the result identifies it as outside scope.

Given a director with a fixture to be added containing a stalled lane whose blocker can be removed within durable authority, and an owner who does not respond, When the director handles the stall, Then the lane resumes progress through the director's delegated remedy and the owner receives no decision request for it.

Given a director with a fixture to be added containing a substantive shared resource investigation, When the director delegates the investigation then records its resource decision, Then the general worker's action history contains the investigation and returned evidence, while the director's contains delegation, result consumption and the decision rather than execution of the investigation.

Given a supervisor with a fixture to be added containing a general worker's diagnosis and candidate diff for a product defect, When the supervisor assigns the implementation then integrates its reviewed result, Then the integrated change comes from an implementer or corrector assignment, not a general-worker commit or ref.

Given a supervisor with a fixture to be added containing a validation failure and an available authorized worker, When the supervisor assigns diagnosis and repair then consumes the result then integrates the worker's change, Then the worker performs the diagnosis and repair while the supervisor retains the lane PR and integration, without taking over the worker's substantive execution.

Given a director with a fixture to be added containing an agent-proposed constraint that blocks a delegated engineering outcome, When the director reconciles the constraint's authority then directs its remedy, Then the responsible supervisor receives an executable decision within the real delegation, and the owner receives no routine permission request.

Given a director with a fixture to be added containing a lane with a completed unconsumed result and a pending owner merge gate, When the director reconciles the lane then handles its wait, Then the result is consumed before any park, and safe unfinished work advances without treating the pending merge as permission to merge.

Given a director with a fixture to be added containing a lane whose owned remedies are exhausted at an owner-held access need, When the director parks the waiting supervisor, Then the lane's wait names the exact blocker, authority holder and wake condition, with no actionable owned work left stranded.

Given the director with a lane whose parent issue is 12, When it starts that lane's supervisor, Then Herdr shows a workspace gh12 holding one tab, supervisor, and the director's workspace is unchanged.

Given the director with a lane in a Linear target whose parent ticket is ENG-123, When it starts that lane's supervisor, Then Herdr shows a workspace eng-123 holding one tab, supervisor, working on branch eng-123, and the director's workspace is unchanged.

Given a supervisor in workspace gh12 with two ready tickets, When it starts an implementer for each, Then Herdr shows both implementers as their own tabs in gh12 and in no other workspace.

Given two agents started through pi-role in two worktrees of one repository, whose stash holds an entry set aside in the first worktree, When the second agent runs git stash drop, Then git refuses it, naming a work-in-progress commit on the agent's own branch as the way to set work aside, and the stash list in the first worktree still shows that entry.

Modular boundaries

Role files own their model, thinking, tools, skills and contract as runtime-neutral data, including the reusable general-worker role. Caller-facing seam: the named role profile and an ordinary assignment brief. Dependency direction: self-contained role data consumed by the launcher; role files do not implement launcher mechanics or per-task policy profiles. Observable scope: the same role resolves to its declared model, thinking, tools and skills for different task briefs.

scripts/pi-role translates a role profile into a Pi start with its declared model, thinking, tools, listed skills and role body. It adds codemode and resolves web tools from the common server list only for roles that list them, with no extra MCPs. General-worker is a recognized role, uses normal operating-model inheritance, and does not require commit identity to start. Caller-facing seam: the named role through herdr-spawn or the same role file for a one-shot run, plus ordinary runtime arguments. Dependency direction: external-provider; the launcher consumes role data, tool/skill resolution and Pi; roles do not construct Pi flags. Target AGENTS.md remains the loaded instruction source. Observable scope: role validation recognizes general-worker, both launch forms resolve the declared profile, and unsupported tools, skills or role metadata fail with a named reason.

herdr-spawn and octo-feather-start own placing agents in workspaces and tabs and recording each tab's parent. Caller-facing seam: just start, just supervise N, and herdr-spawn --role ROLE. Dependency direction: external-provider; they depend on Herdr and call pi-role. Observable scope: Herdr workspaces and tabs.

The supervisor is a delegated goal owner, not a worker executing director commands. Its launch by the director does not create a standing approval dependency for its lane decisions. Director redirection is an explicit change to a goal, priority or constraint within the director's authority, not permission renewed at each step. The supervisor applies that change within its lane ownership and escalates only a genuine outside-envelope conflict; notification or redirection does not introduce an ACK gate. Actual owner gates and safety constraints remain outside any agent's override authority.

The director is accountable for the factory's outcome, as a chief executive is to the owner's board. It runs the program, never the code: it decides what work exists, who owns each piece and in what priority, and answers for the program's overall result. Supervisors and their workers own the implementation and verification of each deliverable; the director judges lane outcomes from their evidence without redoing that verification. Its reports to the owner are its own judgment from that evidence, never a forwarded supervisor or worker summary. When work stalls or fails anywhere, the director diagnoses it and restores progress through delegation, redirection, replacement or reallocation within durable authority, without waiting for the owner. It may inform the owner of any outcome, but expects an owner response only for spec acceptance, merge approval, owner-held access and consequential product or risk decisions. While one of those is pending it stops only the affected action and keeps all other work moving. Accountability does not make the director an executor: substantive work still goes to supervisors and general workers.

Standing authority comes from the role contract, accepted spec, applicable ADRs and durable owner delegation such as the kickoff brief or an owner ruling recorded in the director log. An ordinary task brief supplies goal, expected result, relevant facts and narrower scope; it is not a new permission contract and need not restate existing rights or optional resource details. A missing fact is investigated, not promoted into a prohibition. Escalate only an action excluded by that durable authority or subject to an explicit gate, and stop only the affected action. Safety, isolation, verification and actual resource constraints still bind. Bounded parent notifications are owned by comms.

The director resolves delegated engineering tradeoffs and agent-created constraints before escalating or parking. An agent's proposal is not an owner requirement merely because it appears in a durable artifact. Check the source of authority, execute the owned remedy, record the changed constraint and tradeoff, and route effects through existing spec-call and policy ownership. Do not silently override an explicit owner ruling, genuine access/resource restriction or independent verification requirement. A consequential owner product/risk decision remains an owner decision; escalation names the unresolved choice, evidence, attempted remedies and recommendation.

Delegation-first coordination

Both director and supervisor delegate substantive execution and investigation, retaining their own coordination responsibilities, decision rights and bounded direct operations. The supervisor's lane-goal ownership is not a standing request for director permission.

Immediate containment within authority need not wait for delegation; it does not authorize unrelated execution or waive safety.

When existing lifecycle commands cannot satisfy a real constraint, separate the required operational decision from diagnosis and procedure preparation. Delegate that finite preparation within available authority, preserve the safety constraint, and retain only the bounded authorized control action at the coordinating role. A reusable mechanism change still follows its owning spec and implementation gates; the coordinator does not become its ad hoc implementer.

Judge progress from actual artifacts, diffs, validation, dependencies and live PR/head evidence, not an activity label or a summary alone. The supervisor inspects its worker results; the director inspects consolidated lane evidence and intervenes through the supervisor for a demonstrated mismatch or actionable recovery. The director directly consumes results from its own general workers, not raw results from another goal owner's workers. Green schema or CI alone is not a behavioral verdict; review and QC keep their existing independence and exact-head rules.

Every independent assignment starts with a fresh worker session and a task-fitting brief under its reusable role contract. Do not recycle a live or parked session for unrelated work, even when its model, tools or profile fit. An implementation assignment owns one ticket outcome through integration, review and applicable QC on a head containing it, with no blocking finding assigned to that ticket; the supervisor then closes it, or explicitly cancels or replaces it. A DONE report ends a turn, not that ownership. Same-ticket rework before closure continues the same assignment; a finding no ticket owns becomes a new ticket with a fresh implementer. Applicable QC follows the lifecycle, including its explicit skip; this adds no final-merge wait or unrelated-ticket gate. Fresh independent review and QC judgments remain separate from implementation rework. Follow-up, safe parking and resume are limited to the same unfinished assignment; a new name or tab alone is not freshness. Director and supervisor retain their ongoing goal contexts. The handoff carries goal, constraints, applicable spec anchors, current revision, dependency results, evidence pointers, prior attempts, unresolved needs and next action, sufficient without old chat access, secrets or unbounded transcripts. Replacement still requires diagnosis and single-writer reconciliation, not merely age or DONE.

Reusable general-purpose execution

The general worker is a normal role, not a coordinator, task-specific specialist or caller-authored launch contract. Its fixed tools are read, grep, find, ls, bash, edit, write and web, with normal codemode and herdr-comms; it has no tracker or PR skills. It can perform execution its parent must not do personally, but only within the assigned task and durable authority. It never commits in target repositories or edits target branches, lane worktrees, accepted specs or lane records; product diagnosis returns evidence for an implementer or corrector, not a directly integrated change. Startup does not require factory commit identity for this non-committing role; configured identity can still be present, so this is a contract restriction and accident guard, not a sandbox. Lifecycle-owned mutations go through that lifecycle command and its actual owner. Protection, provenance, scoped destructive actions and truthful measurement apply to every general worker under the common rules below, not only cleanup tasks. Worker-class routing applies to general-worker rather than treating a new role name as unrestricted. It reports to its actual parent, keeps a recoverable result if no allowed parent route is available, and never routes to a peer. Use a unique name and provider-session identity for each independent assignment; only the same unfinished assignment may resume from its recorded identity.

The director, general worker, implementer, corrector, code reviewer and shaper list the web tools; the implementer and corrector also load the agent-browser skill for pages that need a real browser (skills). The supervisor delegates and has neither. Which capability is a tool and which a CLI with a skill: ADR 0016.

The shaper is a utility of the factory, not part of it: it shapes a spec with the owner before the factory sees it (ADR 0021), and talks with the owner directly, the one agent that does besides the director (ADR 0015). It has no lane, lane record, hand-off log or merge ask. Its repair offer in a repository whose specs miss Spec Chat's shaping contract: acceptance-shaper-repair.

The corrector is factory quality, not product quality: it runs only in a correction lane the director starts on a repeat (ADR 0020).

The code reviewer judges what quality spec #quality-reviewer names: code quality, and whether a tagged acceptance test demonstrates its criterion. It loads Matt's code-review with a patch and reads pstack interrogate's code-quality review and lead-judgment references: it blocks only on a documented standards breach or a named simplification that lists the lines it deletes, dismisses a hypothetical case that never happened, and makes smells and scope creep notes. Every finding carries a short class tag so repeats can be counted.

The reflector loads pstack reflect, vendored with a patch for Pi and Herdr: one headless agent reads the records its brief names through the judgment, tooling and divergent lenses and the synthesis step of that skill, and answers the question list (comms #reflection-questions). It proposes no edit and asks for no approval: its lessons are findings (comms #reflection-output).

Launch

Finite director-owned work uses the same general-purpose worker contract, whether it is research, diagnosis, evidence preparation or host maintenance. Task briefs vary; launch modes and permission contracts do not multiply by task kind.

A pane: herdr-spawn --role <role> opens a tab at the declared working directory and starts Pi through pi-role. General-purpose tasks use --role general-worker, not a new per-task launch mode. Product workers retain isolated worktrees. The common operating-model prompt carries applicable target policy to children; the child receives its own role body, not its parent coordinator role identity.

Headless: pi-role agents/<role>.md -p "<brief>" in the worktree, when no conversation is needed; its final message, on stdout, is the report to the agent that ran it.

An agent's launch set is every file its launch hands Pi to make it, as the launcher itself lists them: its role file, the launcher, the kit's web server list, and each skill folder and extension file the launch passes; never the files Pi reads from the working directory on its own, such as the target's AGENTS.md. A pane launch records the set, each file with its content digest, against the agent's session. An agent is stale when the set its role would launch with now, from the same working directory, differs from the recorded one: a digest that differs, a file added or a file gone, each named. An agent with no recorded set is unknown, never current. This is the one launch set: a stored eval run's freshness (quality) asks the launcher for the same files.

Every role, in a pane or headless, gets Pi's codemode tool next to its listed tools: a script that calls those tools, in parallel where it chooses, and returns only what it prints. Codemode calls only tools the session has, so it widens no role's reach: a role without edit or write has no edit or write in its scripts either. Roles run Pi's defaults, codemode.mode on and codemode.inlineBudget 3000: the listed tools stay declared to the model as role contracts and skills name them, so codemode lists none of them again and its listing budget goes unused. The kit sets neither setting.

A role whose tools list web gets web search and page fetch as tools: every tool of each keyless hosted MCP server in the kit's one web server list, Parallel's and Exa's. pi-role reads that list; no role file names a server. Pi's built-in MCP support connects the servers: the list is in Pi's own MCP server format, and the kit adds no MCP client or adapter extension of its own. The web tools are declared to the model like built-in tools and codemode scripts can call them. No other MCP server reaches any role, whether the user's Pi configuration or a target repository names it, and a role that does not list web runs with no MCP at all. When a web server cannot be reached, the role still starts, without that server's tools.

Every agent pi-role launches, in a pane or headless, in any target, runs git through the kit's stash guard: a repository's stash is one list every worktree of it shares, and git offers no stash of a worktree's own, so in a repository with more than one worktree a git stash that adds, removes or replaces an entry is refused, naming a work-in-progress commit on the agent's own branch instead. Reading the stash, every other git command, and any stash in a repository with one worktree run unchanged.

Pi is the only runtime: herdr-spawn refuses any other agent command.

Herdr layout

A lane's key names its workspace, its branch, its lane record and the suffix of its agents' names: gh<N> for GitHub issue N, the lowercased ticket key for a Linear ticket (eng-123 for ENG-123), from the tracker skill's lane-key (ADR 0011). Wherever a recipe takes N, it takes the parent ticket as the tracker writes it: the GitHub issue number or the Linear ticket key.

Each implementer is started under the agent name <role>-<ticket>, lowercase, in a tab labelled worker-<k>; the code reviewer gets tab code-reviewer, and a correction lane's corrector tab corrector. A name is live at most once: the supervisor closes a worker once its result is consumed, before reusing the name.
