Roles, role files and launch

docs / specs / roles.spec.html

Each role is one file in agents/: frontmatter that says how it runs and a body that is its contract. Every agent is Pi, started through herdr-spawn and scripts/pi-role (ADR 0016). Meanings of the role names are in GLOSSARY.md.

User stories

As the owner, a role runs with the same model, tools and skills whether it is in a tab or headless, so a role behaves the same wherever it runs.

As the owner, the code reviewer is never from the same model family as the implementer, so one family's blind spots do not pass their own review.

As the owner, the director cannot edit code, so the agent holding the whole picture never gets pulled into doing the work.

As the owner watching the factory, each work item has its own workspace with its supervisor and workers, and the director has its own.

As a maintainer, a role file the launcher cannot honour fails the gate before any agent starts with it.

Acceptance criteria

Given a supervisor, When it starts a code reviewer in a worker tab, then starts one headless on the same head, Then both reviewers report the same model, thinking level, tools and skills, and both have loaded the target repository's AGENTS.md.

Given a maintainer, When any change sets the code reviewer's model to the implementer's model family, Then the gate fails, saying the reviewer must use a different family.

Given a maintainer, When any change adds a frontmatter key the launcher does not honour to a role file, Then the gate fails naming the file and the key.

Given a maintainer, When any change lists a skill in a role file that the kit does not hold, Then the gate fails naming the file and the skill.

Given a maintainer, When any change sets a role's model to one outside the allowed list, Then the gate fails naming the file and the model.

Given a box whose global Pi skill folder holds skills no role file lists, When the supervisor starts an implementer, Then the implementer has loaded exactly the skills its role file lists and none of the global ones.

Given the owner, When the owner starts the director and opens its tab, Then the director's tools are read, grep, find, ls and bash, with no edit or write tool.

Given the director with GitHub issue 12 open, When it starts that item's supervisor, Then Herdr shows a workspace gh12 holding one tab, supervisor, and the director's workspace is unchanged.

Given a supervisor in workspace gh12 with two ready tickets, When it starts an implementer for each, Then Herdr shows both implementers as their own tabs in gh12 and in no other workspace.

Modular boundaries

Role files own each role's model, thinking, tools, skills and contract, as runtime-neutral data. Caller-facing seam: the frontmatter keys above and the contract body. Dependency direction: self-contained; launchers read role files and role files name no launcher. Observable scope: what each started agent reports it runs with.

scripts/pi-role owns turning a role file into a Pi start: model, thinking, the tool allowlist, only the listed skills, no MCP, the body appended to the system prompt. Caller-facing seam: pi-role agents/<role>.md, with -p for headless runs. Dependency direction: external-provider; it depends on Pi. Pi loads the target's AGENTS.md from the working directory. Observable scope: the started Pi session.

herdr-spawn and octo-feather-start own placing agents in workspaces and tabs and recording each tab's parent. Caller-facing seam: just start, just supervise N, and herdr-spawn --role ROLE. Dependency direction: external-provider; they depend on Herdr and call pi-role. Observable scope: Herdr workspaces and tabs.

Corrector (worker)agents/corrector.mdanthropic/claude-opus-5-5, mediumCommits from pstack correct, in its own worktree off the integration headFresh per merge, before review: a worker tab, or headless
Code reviewer (worker)agents/code-reviewer.mdopenai/gpt-6.1-sol, highNothing: returns a verdictFresh per merge: a worker tab, or headless

Integration is not a role: the supervisor runs just integrate N, a script (ADR 0017). The owner is the person, not an agent.

The supervisor owns its work item until it merges and never implements, self-reviews, accepts, or addresses the owner.

The code reviewer loads Matt's code-review with a patch: it blocks only on a failed acceptance criterion, broken behavior or a hard standard; smells and scope creep are notes.

Role file format

Role file frontmatter: only these keys, one key: value per line
KeyMeaning
nameEquals the file name
descriptionOne line for readers; not passed to the agent
modelA model the deployment's model proxy serves, from the allowed list
thinkingThinking level
toolsStrict allowlist of built-in Pi tools, comma-separated
skillsThe only kit skills the role loads, by name (see skills)
externalSkillsOptional: skills installed outside the kit, such as Spec Chat's, looked up on the box's external skill path at launch; a missing one is skipped with a warning

Role files carry no repo instructions: every role inherits the target repository's AGENTS.md, which Pi loads from the working directory.

Launch

A pane: herdr-spawn --role <role> opens a tab at the given worktree and starts Pi through pi-role.

Headless: pi-role agents/<role>.md -p "<brief>" in the worktree; the final message is the report.

Pi is the only runtime: herdr-spawn refuses any other agent command.

Herdr layout

Each worker is started under the agent name <role>-<ticket>, lowercase, in a tab labelled worker-<k>. A name is live at most once: the supervisor closes a worker once its result is consumed, before reusing the name.
