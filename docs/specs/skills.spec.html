Skills and their sources

docs / specs / skills.spec.html

Skills are plain folders in .agents/skills/, the cross-client Agent Skills location (ADR 0018). Skills with an upstream in Matt Pocock's skills or pstack are vendored from it and patched only where a decided ADR needs it; octo-lite supplies requirements, not skill text.

User stories

As a maintainer, every skill with a Matt or pstack equivalent uses that upstream text plus a small patch, so the kit stays lighter than octo-lite and picks up upstream fixes.

As a maintainer, every patch says on its first line which decision it serves, so I can tell whether it is still needed.

As the owner, each role loads only the skills its role file lists, so one role's instructions never leak into another.

As the owner, I choose for each target repository whether its tickets live in GitHub Issues or Linear, and every agent working on it loads only that tracker's skill, while review and merge stay on GitHub.

As the owner, the agents that build and fix can drive a real browser, so they can check a page, a form or a documentation site that only works with a browser.

As the owner, every vendored skill's licence and author is credited, so the kit can be shared.

Acceptance criteria

Given a maintainer, When any change edits the text of a vendored skill, Then the edit lands as a patch in the skill's patch folder whose first line names the ADR it serves, and re-applying the pinned upstream with its patches reproduces the committed skill.

Given a maintainer, When any change adds a skill without a name or description in its frontmatter, Then the gate fails naming the skill.

Given a supervisor in a target repository that has its own skills folder, When it starts an implementer there, Then the implementer has exactly the skills its role file lists available, and none from the target's folder or the kit's by discovery.

Given a target repository holding a skill Pi cannot load, which the implementer's role file lists or the target's AGENTS.md declares on its Repo skills: line, When a supervisor starts an implementer there, Then no implementer starts, and the supervisor is told which skill Pi did not load and Pi's reason.

Given a box with Spec Chat's skills installed for the user, When the director starts a supervisor, then the supervisor needs a change to its accepted spec, Then the lane's pull request shows that spec change logged as a judgement call by that supervisor, and the supervisor has shaped nothing else.

Given a target repository whose AGENTS.md declares its verify skill on its Repo skills: line, When an implementer, a corrector or the just qc judge starts a task there that drives the app, Then that agent reads the verify skill and any other skill the target declares that its task needs, and every skill its role lists stays available to it.

Given a maintainer, When an agent reads either vendored verification skill, Then it names .agents/skills as the skills folder, loading a skill by name, the supervisor where upstream asks the user, and the agent's own serial reads where upstream starts subagents, and it names no .cursor/ path and no slash command.

Given a target repository whose config selects Linear, When the director starts a supervisor for it, Then the supervisor has the github-pr and linear skills available and not github-issues.

Given a target repository with no tracker in its config, When the director starts a supervisor for it, Then the supervisor has the github-pr and github-issues skills available and not linear.

Given a target repository whose config names a tracker the kit has no skill for, When the director starts a supervisor for it, Then no supervisor starts, and the director is told the tracker is unknown and which trackers the kit has.

Given a maintainer, When any change leaves a tracker skill without one of the tracker scripts, Then the gate fails naming the skill and the missing script.

Given a supervisor on a box whose install check passes, When it starts an implementer, then the implementer is asked to open a web page and say what it shows, Then the implementer has the agent-browser skill available and answers from that page as a real browser rendered it, using the agent-browser release the skill is pinned to.

Given a maintainer, When any change vendors a new upstream skill, Then NOTICE names that skill with its upstream, pin, licence and author.

Modular boundaries

The Skillfile owns which upstream skills are vendored, at which pin, and how patches are kept across updates. Caller-facing seam: Skillfile, Skillfile.lock and .skillfile/patches/skills/<name>/. Dependency direction: external-provider; it depends on the upstream repositories and the skillfile tool. Observable scope: the committed folders in .agents/skills/.

pi-role owns which skills a role gets: discovery off, one load per listed skill, {tracker} replaced by the target's tracker skill, external skills from the target repository's .agents/skills. Caller-facing seam: the role file's skills and externalSkills keys, and the target's .octo-feather.toml. Dependency direction: self-contained over the kit checkout, the repository's .agents/skills and its .octo-feather.toml. Observable scope: the skills a started agent reports.

The tracker skills, github-issues and linear, own every read and write of tickets in their tracker; github-pr owns branches, pull requests and merges. Caller-facing seam: the tracker scripts below, the same names, arguments and output in each tracker skill, at .agents/skills/<tracker>/scripts/<name>. Dependency direction: external-provider; github-issues and github-pr depend on the gh CLI, linear on the linear CLI. The kit's general scripts call the tracker scripts and hold no tracker-specific code; no tracker skill calls the kit. Observable scope: tickets in the target's tracker, and pull requests on GitHub.

Tracker skills

A target repository names its tracker in .octo-feather.toml at its root: tracker = "github" or tracker = "linear", github when the file or key is absent (ADR 0004).

Each tracker skill, and github-pr, is self-contained: .agents/skills/<name>/ holds its SKILL.md and a scripts/ folder with every script it needs, as herdr-comms does. Each script is a thin wrapper over one command of its tracker's CLI: gh for github-issues and github-pr, linear for linear. The linear skill holds only the tracker scripts, and says that lane operations (view, create, comment, done, lane key, pull request line) go only through them; for any other read the agent reads the vendored linear-cli skill's references by path, as it reads gh's own help on the GitHub side. github-pr also ships the offline fake gh that the kit's tests use and the just qc judge also runs. The linear skill ships no test code: the kit's tests stand in for linear at its command line with recorded answers kept beside the tests.

A role file lists {tracker} among its skills where it needs ticket work, and pi-role loads the target's tracker skill in its place, and nothing else for the tracker: no role loads linear-cli. Role prose and every other kit skill say "the tracker skill" and never name gh issue commands or Linear.

Where skills live and how they load

Every kit skill, vendored or local, is a folder in .agents/skills/; role files stay in agents/.

A role has exactly the skills its file lists available: discovery is off for every role, so neither the kit's nor a target repository's .agents/skills loads by itself. A target's own skills reach an implementer, a corrector or the just qc judge only when the target's AGENTS.md declares them on its Repo skills: line and the agent loads them by name; the target's verify skill reaches them this way (quality spec #verify-skill).

Pi leaves out a skill it cannot load, such as one whose frontmatter is not valid YAML, and still starts. So a role starts only when Pi loads every skill its file lists and every skill the target declares on its Repo skills: line; otherwise the launch refuses before any model call, naming each skill Pi did not load and Pi's reason. What Pi loaded is Pi's own answer, never a parse of the skill files, and the gate asks Pi the same for every kit role.

Skills installed outside the kit, such as Spec Chat's, are named under externalSkills and found only in the target repository's .agents/skills, the working checkout's and then its main checkout's, never in a home folder (ADR 0013). A target repository gets Spec Chat only as links in its .agents/skills, never as .claude/ or .codex/ links (ADR 0001). The supervisor lists Spec Chat's shaping and review skills, and uses shaping only to make the spec changes its logged calls record (ADR 0021); shaping itself happens with the shaper (#loading-shape, ADR 0021).

Shaping runs in the shaper role, a utility outside the factory (roles, ADR 0021): agents/shaper.md owns its skills, the kit's that the table above names as loaded by the shaper and Spec Chat's under externalSkills, and the step each is read at (ADR 0012). just shape, run in the target repository, starts it through pi-role, as any role starts (ADR 0016). The kit's AGENTS.md names it in one line.

The agent-browser skill is a short guide that has the agent load the full usage guide from the installed CLI (agent-browser skills get core), so the box runs the CLI at the release the skill is pinned to, and the two move together.

From pstack the kit vendors correct, principle-prove-it-works, principle-build-the-lever, principle-encode-lessons-in-structure, blast-radius, sharpen, create-verification-skill, maintain-verification-skill, reflect, poteto-mode's refactoring playbook alone as the skill refactoring with the three principles it relies on (principle-laziness-protocol, principle-subtract-before-you-add, principle-minimize-reader-load), and interrogate, whose code-quality review and lead-judgment references the code reviewer reads; it leaves out show-me-your-work, swarm and the rest of poteto-mode.
