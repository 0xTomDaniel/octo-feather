The kit is stack-agnostic: a target repository starts from one of two templates, Python or TypeScript, that already carry a strict gate, an app CLI and a target AGENTS.md, so agents land on a codebase that resists sloppy changes (ADR 0008).

User stories

As the owner starting a new project, I pick Python or TypeScript and get a repository whose gate already rejects type errors, lint, structure breaks and failing tests.

As an implementer, I verify my work through the app's CLI with --json, the same surface the end-to-end tests and the product judge use (ADR 0009).

As an implementer in a template-born repository, I prove my change by driving the app through the repository's verify skill from its first commit, so no lane has to build one first.

As an implementer in a template-born repository, the starter command already validates its input with the stack's schema library, so I extend one working edge instead of inventing one (quality spec #acceptance-edge-validated).

As the owner, the full gate CI runs is the gate a lane's merge readiness requires, and the fast check agents and the git hook run is part of it, so green means the same thing everywhere.

Acceptance criteria

Given the owner with a new repository from either template, When the owner runs its gate, Then the gate passes and reports lint, types, structure and tests each as checked.

Given an implementer in a repository from either template, When it commits a change with a type error, Then the commit is refused by the gate, naming the file and line.

Given an implementer in a repository from either template, When it adds an import that crosses a forbidden layer, Then the gate fails naming the rule broken.

Given an implementer in a repository from either template, When it runs any app command with --json, Then the command prints one JSON document describing the result.

Given an implementer in a new repository from either template, When it gives the starter command its input as a JSON request holding a field the command does not know, with --json, then gives it the same request without that field, Then the first run fails, printing one JSON document that names the unknown field, and the second prints one JSON document holding the greeting.

Given the owner, When a change is pushed to main of a template-born repository, or to its pull request once that pull request is ready for review, other than a push that adds only just qc's status-only commits (issue-lifecycle #lanes-one-head), Then CI runs the full gate, just check, the one a lane's merge readiness requires, and a red result blocks the pull request.

Given an implementer in a new repository from either template, When it changes one source file of the app, then runs just fast, Then lint, types and structure are checked, then only the integration tests the stack's own test impact tool picks for that file run, and the output names them.

Given an implementer in a new repository from either template, When it runs just check, then changes the app's core and runs just fast, Then the first run shows its integration tests and its end-to-end tests each by kind, and the second shows no end-to-end test.

Given an implementer in a new repository from either template whose tests share a prepared fixture, When it runs just check with several workers, Then the run shows that fixture prepared once, and every test that used it passed against it unchanged.

Given the owner with a new repository from either template, When an implementer starts in it, Then the implementer has loaded the repository's AGENTS.md, which names the gate and the repository's own skills.

Given the owner with a new repository from either template, When an implementer runs just check, then just qc on the starter criterion, Then the qc report judges the starter criterion from the record its tagged acceptance test left in that just check, and no separate demo runs for it.

Given the owner with a new repository from either template, When an implementer runs the repository's verify skill end to end on its starter feature, Then the skill launches the app, passes its doctor, drives the app CLI with --json and keeps its evidence after cleanup, and the repository's AGENTS.md names that skill on its Repo skills: line.

Modular boundaries

Each template owns a starter repository: toolchain, gate, app CLI, tests and target AGENTS.md. Caller-facing seam: just check and just fast, the app CLI with --json, and the AGENTS.md Repo skills: line. Dependency direction: self-contained; a template names no kit path and the kit reads only those seams. Observable scope: the generated repository and its gate output.

End-to-end and integration tests drive only the interfaces and seams quality spec #acceptance-public-surfaces allows; there are no unit tests of internals (ADR 0002). Which tests are end-to-end, and how an integration test stands in for what is slow or external: quality spec #test-kinds. A template's integration test feeds the command minimal inputs in a cheap fixture and takes well under a second; each user-facing flow keeps one end-to-end test. Which tier runs which kind: quality spec #recipes-table.

Templates live in the kit at templates/python and templates/typescript; the kit's own gate checks each template's wiring.

A repository created from a template has a just integrate recipe that calls octo-feather-integrate; both templates ship one, and the kit's check-templates fails a template without it. A repository the kit did not create gains no factory recipe: agents run octo-feather-integrate and octo-feather-qc directly (ADR 0017).

The owner creates a repository from a template with a just recipe in the kit that copies the template.
