Lifecycle: accepted spec to merge

docs / specs / issue-lifecycle.spec.html

How an accepted spec becomes lanes, how one lane moves to its merge ask, which steps stop the line, and what the owner decides. A lane is one merge ask on one parent GitHub issue (ADR 0019). Roles are in roles; messages and lane state in comms; the gate recipes in quality.

User stories

As the owner, I shape and accept a spec in my own chat before the factory sees it, and the factory builds only a spec I accepted.

As the owner, each lane reaches me as one merge ask on one parent issue, relayed by the director, already carrying every piece of evidence I need to decide.

As the owner, every ticket on a lane is a thin path I could demo, so progress on the parent issue means working behavior, not half-built layers.

As a supervisor, my first ticket runs alone end to end, so a bad brief, check or ticket size fails once instead of in every worker.

As a supervisor, I combine my workers' branches with a script that either lands all of them with a green gate or lands nothing, so conflicts never get resolved by guesswork.

As the owner, a wording-only correction to a spec I accepted rides on my acceptance, while any change to what the spec makes the system do comes back to me.

As the owner, a work item that the spec on main already states goes straight to a lane with no new spec review.

As the owner, a mistake that repeats gets fixed in the factory once, in its own lane, without holding up product work.

Acceptance criteria

Given the owner with a spec that has not been accepted, When the owner tells the director to build it, Then the director tells the owner the spec is not accepted and why, and GitHub shows no new parent issue and Herdr no lane workspace or supervisor tab for it.

Given the owner with an accepted spec, When the owner tells the director to build it, Then GitHub shows one new parent issue per lane the director cut, and Herdr shows one lane workspace per parent issue holding its supervisor.

Given the owner with an accepted spec built into a lane, When the lane's draft pull request opens, then the owner opens it, Then its branch starts at the accepted commit, and the pull request shows exactly one receipt comment, naming the owner's Accept spec action, its date, the spec path and the accepted commit, recorded by the director.

Given a supervisor starting a lane, When it files the lane's tickets, then the owner opens the lane's parent issue, Then the parent issue lists every ticket as a sub-issue, and a ticket shows Blocked by only where it must wait for another.

Given a supervisor, When any lane's tickets are filed, Then every ticket names the acceptance criteria it serves and ends on a demo path through the app's CLI, HTTP or UI, and none is a layer-only ticket outside a wide refactor's expand-and-contract sequence.

Given a supervisor with several ready tickets, When it starts delivery, then the owner opens the lane's workspace, Then the workspace holds one implementer tab, for the first ticket, and no second implementer tab appears until that ticket has been integrated and reviewed.

Given a supervisor with two finished implementer branches that change the same lines, When the supervisor integrates both, Then the lane branch is where it was before the second merge and the supervisor is told it stopped on a conflict, proven by an integration test: no screen shows it.

Given a supervisor with a finished implementer branch that turns the gate red, When the supervisor integrates it, Then the lane branch is where it was before and the supervisor is told the gate is red, proven by an integration test: no screen shows it.

Given a lane whose final head passed review, When the owner reads the merge ask the director relays, Then it names the head, shows required checks passing, links the review verdict and the lane's acceptance receipt, and lists every failed product criterion with its triage.

Given any change on a lane, When its supervisor sends the merge ask, Then a code reviewer from a different model family than the implementer, started fresh for that head, has judged it, and no worker reviewed its own work.

Given the owner with an accepted spec built into a lane, When the supervisor commits a correction that only rewords that spec, then the owner opens the lane's pull request, Then the pull request body names that commit as wording-only in one line, and the pull request shows no new acceptance receipt for it.

Given the owner with an accepted spec built into a lane, When the supervisor needs a spec change that alters a behavior the spec states, Then the owner receives a review link for that change from the director before any merge ask.

Given the owner with a work item whose behavior the spec on main already states, When the owner tells the director to build it, then opens the lane's pull request, Then no spec review was asked, and the pull request shows the work, a review verdict and passing required checks.

Given a finding class that code review has now logged twice across lanes, When the director checks finding classes after the next merge ask, Then GitHub shows a new parent issue for a correction lane naming that class, Herdr shows its workspace with one corrector, and every product lane keeps running.

Given the owner who corrects an agent's work at a merge gate, When the director handles that correction, Then GitHub shows a new correction lane's parent issue quoting the owner's correction.

Modular boundaries

An owner chat owns shaping, using Spec Chat's shaping skill on the spec's own branch; the review host owns the acceptance record. Caller-facing seam: the accepted spec path and its acceptance on the review host. Dependency direction: external-provider; the factory reads acceptance and never shapes. Observable scope: the review page and its Accept spec action.

The director owns kickoff: checking acceptance, cutting lanes, filing parent issues, branching lanes from the accepted commit, recording receipts, and starting correction lanes. Caller-facing seam: the owner's build request, octo-feather-accepted SPEC_PATH (exit 0 with the accepted commit, else the reason), and the director's lane start. Dependency direction: external-provider; it uses the review host, GitHub and the Herdr wrappers. Observable scope: parent issues, lane workspaces and receipt comments.

The supervisor role and the vendored implement-spec skill own one lane: tickets, the pilot, briefs and the merge ask. Caller-facing seam: the lane brief the director sends and the merge ask the supervisor sends back. Dependency direction: external-provider; the supervisor uses the integrate script, the Herdr wrappers and GitHub, and nothing calls it but its director. Observable scope: the lane's workspace, its sub-issues and pull request.

The integrate script owns landing named worker branches or commits on one lane branch with a green gate, all or nothing. Caller-facing seam: just integrate N REF... and its exit status (0 landed, 1 conflict, 2 red gate). Dependency direction: self-contained over git and the target's just check; it never pushes and calls no model. Observable scope: the lane branch head.

GitHub owns parent issues, sub-issues, pull requests, receipt comments and merges as the durable record of delivery. Caller-facing seam: the gh CLI. Dependency direction: external-provider. Observable scope: issues, pull request comments and merge commits.

The line

Lanes and tickets

One lane is one supervisor, one merge ask and one parent GitHub issue, filed by the director. The director cuts lanes from the accepted spec with no numeric cap: usually one spec is one lane; a big spec whose outcomes can merge independently becomes several; several small coupled specs become one; code that must change together stays in one lane.

The supervisor decides ticket count, order, cuts and the worker split. Tickets are sub-issues of the lane's parent, with Blocked by only where order matters. Every ticket is a tracer bullet: a thin path through every layer, ending on a demo path through the app CLI, HTTP or UI, naming the acceptance criteria it serves.

The first ticket is the pilot: it runs alone through brief, one implementer, just integrate, just qc and code review. The supervisor then fixes its brief template, re-cuts the remaining tickets and fans out.

A correction lane is an ordinary lane whose work is factory quality: the director starts one when the owner corrects something at a gate, or when a finding class appears two or more times across lanes. It has its own parent issue, supervisor, one corrector, code review and a small merge ask, and no product lane waits on it (ADR 0020).

Owner gates

Spec acceptance and merge are the owner's gates, and so are any acceptance of unaccepted work, promotion and live traffic changes. No agent decides any of them.

Shaping and spec acceptance happen outside the factory: the owner's chat shapes the spec and registers it under the spec's own slug, and the review host's acceptance is the record. The factory starts when the owner tells the director to build an accepted spec.

Every later gate reaches the owner through the director: the supervisor sends a review link or the merge ask up with herdr-say --parent and never addresses the owner (ADR 0015).

The review host's accepted registration is the record of spec acceptance. When a supervisor reports its lane's draft pull request, the director records one receipt comment on that pull request, naming the owner's Accept spec action, its date, the spec path and the accepted commit, and itself as recorder; each lane pull request gets its own. Delivered work is recorded by the agent receiving the merge instruction, as a receipt on the pull request before it merges. The spec reaches main with the first lane that merges.

The supervisor may commit spec corrections that change only wording, labels or anchors, add or remove no criterion, and change no stated behavior, value or outcome; these keep the original acceptance, and the supervisor lists each in the pull request body. Anything it cannot plainly call wording-only is a spec revision made with spec-chat-shape, whose review link goes up through the director for a fresh acceptance before any merge ask.

A work item whose behavior the spec on main already states needs no shaping and no new acceptance: it goes straight to a lane, and that spec's commit on main is the acceptance receipt.

Before the merge ask, the supervisor triages every product criterion the product judge failed: a code fault gets a repair ticket worked by a fresh implementer; a fault in how the criterion was judged is fixed and re-judged; a failure in behavior the lane did not change is listed as outside the lane with the reason. Every verdict the merge ask lists was judged at the merge ask's head.
