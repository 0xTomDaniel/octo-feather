Lifecycle: accepted spec to merge

docs / specs / issue-lifecycle.spec.html

How an accepted spec becomes lanes, how one lane moves to its merge ask, which steps stop the line, and what the owner decides. A lane is one merge ask on one parent issue in the target's tracker, GitHub Issues or Linear (ADR 0004, ADR 0019); pull requests and merges are always on GitHub. Roles are in roles; messages and lane state in comms; the gate recipes in quality.

User stories

As the owner, I shape and accept a spec in my own chat, a shaper agent's chat included, before the factory sees it, and the factory builds only a spec I accepted.

As the owner, each lane ends in one merge ask on one parent issue, already carrying every piece of evidence a decision needs, and the director relays it to me only when it holds something only I can decide.

As the owner, a lane whose proof is complete and that holds nothing only I can decide merges without me, and one daily digest tells me what merged, so I gate decisions, not merges.

As the owner, when I say merge, the work I approved lands on main as I approved it: the head I approved, or that head with only a clean merge of main into it, and any other change to the lane comes back to me as a new merge ask instead of being forced through.

As the owner, main tells me which criteria of each accepted spec are planned and which are built, and by which pull request, without the spec I accepted changing.

As the owner, every ticket on a lane is a thin path I could demo, so progress on the parent issue means working behavior, not half-built layers.

As the owner, each ticket names the skills its worker must load, and I can see which of them the worker never loaded, so a skill the work needs is part of the work, not a hope.

As a supervisor, my first ticket runs alone end to end, so a bad brief, check or ticket size fails once instead of in every worker.

As the owner, the code review and the product judge I read in a merge ask judged the same head, and the head I would merge differs from it only by the product judge's status commit.

As the owner, after a lane's head changes, above all by a merge of main, the lane redoes only what the change moved, so a refreshed merge ask reaches me in minutes, not an hour.

As a supervisor, I combine my workers' branches with a script that either lands all of them with a green gate or lands nothing, so conflicts never get resolved by guesswork.

As the owner, when a build shows that a spec I accepted must change, the spec and the code change together without waiting on me: a change that adds to or weakens what I accepted waits for my approve or deny before it merges, a change that only clarifies merges and reaches me in the digest, and spec and code never diverge.

As the owner, a work item that the spec on main already states goes straight to a lane with no new spec review.

As the owner of a Linear-first repository, my lanes are reviewed and merged on GitHub while their tickets live and finish in Linear, and no agent files a GitHub issue for them.

As the owner, a mistake that repeats gets fixed in the factory once, in its own lane, without holding up product work.

As the owner, when main moves, the director's checkout moves with it and every agent still running on an older launch is named, so a stale factory is a state I can see, never one I find by chance.

As the owner, a lane's merge carries main's move, the lane's archive and its teardown through in order with no command from the director, and I hear of each merge once, so the director is never the factory's clock.

As the owner, the director starts every lane, for the kit or any target, with one command that does the whole start, so no lane starts from a stale kit, under another lane's issue, or half set up.

As the owner, the factory starts no new lane while the Claude account's weekly use is on course to pass its reserve before the reset, or while the box already holds its limit of open lanes, so the week never runs out and I am not the brake.

Acceptance criteria

Given the owner with a spec that has not been accepted, When the owner tells the director to build it, Then the director tells the owner the spec is not accepted and why, and the target's tracker shows no new parent issue and Herdr no lane workspace or supervisor tab for it.

Given the owner with a newly accepted spec that has no existing status, When the owner tells the director to build it, Then GitHub shows a spec pull request from spec/<slug> whose only commit after the accepted one adds docs/specs/<slug>.status.json with every criterion planned, its body cites the acceptance id and the accepted commit, and no lane parent issue exists while it is open.

Given the director with a verified owner-accepted spec revision, existing tracked built criteria with their PR and evidence metadata, and a newly added criterion, When it initializes the revised spec's status, Then matching criteria retain their complete existing results and metadata, the new criterion is planned, and the acceptance baseline is the verified revised commit.

Given the director with a verified owner-accepted spec revision that removes a criterion, When it initializes the revised spec's status, Then active statuses name exactly the revised spec's criteria and the removed result remains available in Git history.

Given the director with an initialized accepted revision whose newly added criterion a lane has since built, When it repeats initialization for that accepted revision, Then all existing results, including that criterion's built result and evidence metadata, remain unchanged.

Given the director with an accepted revision and existing status containing incomplete evidence metadata, When it initializes the revision's status, Then initialization refuses naming the invalid metadata and leaves existing status unchanged.

Given the owner who tells the director in chat that a spec is accepted without pressing Accept spec, When the owner tells the director to build it, Then the director refuses it as not accepted, naming the Accept spec button as the only way to accept, and no spec pull request opens.

Given the owner with an accepted spec, When the owner tells the director to build it, then opens the target's tracker and Herdr once the supervisor the director names has merged its spec pull request, Then the target's tracker shows one new parent issue per lane the director cut, and Herdr shows one lane workspace per parent issue holding its supervisor.

Given a merged spec pull request, When a lane for that spec opens its draft pull request, then the owner opens it, Then the lane branch starts from a main that holds the spec and its status file, and the spec file in the pull request differs from the accepted commit's only by changes its logged calls name.

Given a lane whose merge ask lists the criterion ids it builds, When the owner merges it, then opens the spec's status file on main, Then exactly those criteria read built with that pull request's number, in the same merge commit as the lane's code, and every other criterion is unchanged.

Given a status file whose ids differ from its spec's criteria by one missing, extra or duplicated id, or that marks a criterion built without a pull request, When just check runs, Then the gate fails and its message names the status file and the offending id, proven by an integration test: no screen shows it.

Given a supervisor starting a lane, When it files the lane's tickets, then the owner opens the lane's parent issue, Then the parent issue lists every ticket as a sub-issue, and a ticket shows Blocked by only where it must wait for another.

Given a supervisor, When any lane's tickets are filed, Then every ticket names the acceptance criteria it serves, or, serving none, the rule it serves and that rule's owner, an ADR or an owner ruling, and ends on a demo path through a public interface the product offers its users (its CLI, HTTP, UI, MCP or another public protocol), and none is a layer-only ticket outside a wide refactor's expand-and-contract sequence.

Given a supervisor whose lane ticket names a skill its worker must load, When the worker hands off its result without having loaded that skill, Then the lane's hand-off log records the miss, naming the ticket and the skill, and the supervisor sends the worker back once to load the skill before its work is integrated.

Given a supervisor with several ready tickets, When it starts delivery, then the owner opens the lane's workspace, Then the workspace holds one implementer tab, for the first ticket, and no second implementer tab appears until that ticket has been integrated and reviewed.

Given a supervisor whose pilot ticket was just integrated, When it records the pilot's results then the owner opens the lane's draft pull request, Then the pull request exists, its status file marks the pilot's passed criteria built with that pull request's number in a status-only commit, and the pilot's review verdict names the head that commit follows.

Given a lane that builds at least one criterion, ready for its merge ask, When the owner reads the merge ask, Then the code review verdict and the qc report name the same judged head, the qc report named every criterion the lane builds, and the head the merge ask names differs from the judged head only by qc's status commit and any merge of main that left the lane's own diff unchanged, each with its check's proof.

Given a lane whose judged head has clear qc and review verdicts and changed one part of a file, needs an induced failure: main changes another part of that file, When the supervisor merges main into the lane with no conflict, then runs the merge ask check, Then the check passes keeping both verdicts with no new judge run, naming the judged head, the refreshed head and its proof that the lane's own changes are unchanged, proven by an integration test: no screen shows it.

Given an integrated lane head whose lane builds three criteria, When the supervisor runs just qc naming all three and one fails, Then the qc report shows one result per named criterion, each with its evidence state, its decision source and the evidence record it was judged from, and the new head's only change is the status file, marking the two passed criteria built and the failed one planned.

Given a supervisor past its pilot with two ready tickets that do not block each other, When it fans out, then the owner opens the lane's workspace, Then the workspace shows two implementer tabs working at the same time.

Given a supervisor with two finished implementer branches that change the same lines, When the supervisor integrates both, Then the lane branch is where it was before the second merge and the supervisor is told it stopped on a conflict, proven by an integration test: no screen shows it.

Given a supervisor with a finished implementer branch that turns the gate red, When the supervisor integrates it, Then the lane branch is where it was before and the supervisor is told the gate is red, proven by an integration test: no screen shows it.

Given a supervisor past a pilot that passed the full gate, with a finished implementer branch that touches no path the shared-machinery list names, When the supervisor integrates it, Then only the fast tier runs and the supervisor is told the new head is provisional, proven by an integration test: no screen shows it.

Given a supervisor with a finished implementer branch that renames a file the shared-machinery list names and turns the full gate red, When the supervisor integrates it, Then the lane branch is where it was before and the supervisor is told the full gate ran for that file and is red, proven by an integration test: no screen shows it.

Given a supervisor integrating its lane's first ticket, When the integration lands, Then the full gate ran on that head and its pass is recorded against that head, proven by an integration test: no screen shows it.

Given a supervisor in a repository the kit did not create, which has only its own gate, When the supervisor integrates a finished branch, Then that gate runs in full and the repository gains no recipe, proven by an integration test: no screen shows it.

Given a lane whose final head has no recorded full gate pass for that head and the gate's configuration, When the supervisor runs the merge ask check, Then it refuses, naming the head and the missing full pass, proven by an integration test: no screen shows it.

Given a lane whose full gate on its final head took longer than the repository's gate-time budget, When the owner reads the merge ask the director relays, Then it shows that wall time flagged over the budget, beside the trend and the slowest items.

Given a supervisor whose lane's final head passed the full gate, When it starts just qc and the code review on that head, Then the lane's pull request shows CI's full run on that head already started, before either verdict is in.

Given a lane whose judged head passed CI, When the supervisor pushes just qc's status-only commit, then runs the merge ask check, Then CI starts no new full run for that commit, and the check passes on the judged head's CI, naming that head.

Given a lane whose judged head has a clear review verdict, needs an induced failure: main changes a line the lane also changed, When the supervisor merges main into the lane resolving that conflict, has a fresh code reviewer review the merge, then runs the merge ask check, Then the reviewer's verdict names the merge and only the files its resolution changed, and the check passes on the earlier verdict with that one, proven by an integration test: no screen shows it.

Given a lane whose final head passed review, When the owner reads the merge ask the director relays, Then it names the head, shows required checks passing, gives each criterion's qc verdict and links the review verdict, lists the criterion ids qc flipped to built, and lists every failed product criterion with its triage.

Given a lane ready for its merge ask, and two other open lane pull requests, one whose product judge demo pins a stored eval run of a role whose launch set this lane changes and one whose head conflicts with this lane's head, When the supervisor runs the merge ask check, Then its report names the first pull request with that pinned run and the changed files, and the second with the conflicting files, and the check passes as it would without them, proven by an integration test: no screen shows it.

Given a lane whose brief names no criterion and whose final head passed review, When the owner reads the merge ask the director relays, Then it names the head, shows required checks passing, links the review verdict for that head, and says the lane builds no criterion, with no qc verdict and no criterion flipped to built.

Given a lane whose posted review verdict holds only a review of its last fix, not one of the lane from main, When the supervisor runs the merge ask check, Then it refuses, naming the range the verdict covers and the range of the lane no posted review covers, proven by an integration test: no screen shows it.

Given a lane whose review verdict classes a check it adds as resting only on a field the work's producer declared, When the owner reads the merge ask the director relays, Then it shows that check as a declaration stopgap, apart from the exact checks, and the merge ask passes as it would without it.

Given a correction lane whose review verdict lists a check it adds and whose parent issue lists the findings that made it due, When the supervisor runs the merge ask check with no replay of that check, Then it refuses, naming each finding with no replay, proven by an integration test: no screen shows it.

Given a correction lane whose merge ask replays its new check on every finding its parent issue lists and on the clean lanes the check names, When the supervisor runs the merge ask check, Then it passes and shows how many of the findings the check caught and how many clean cases it refused, each from its own run of the check.

Given the owner who said merge to a lane's merge ask, with the lane branch unchanged since the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the lane's pull request merged by the supervisor at the head the merge ask named, and the target's tracker shows its parent issue done.

Given the owner of a Linear target who said merge to a lane's merge ask, When the director relays that merge to the lane's supervisor, then the owner opens the lane's parent ticket in Linear, Then Linear shows the parent ticket and every one of its tickets done.

Given the owner of a Linear target whose lane merged, When the owner opens the lane's pull request on GitHub, Then it shows merged, its body tracks the parent ticket by its Linear key, and it links no GitHub issue to close.

Given the owner of a Linear target whose lane merged, When the owner opens the repository's issues on GitHub, Then the list holds every issue it held before the lane started and none filed since by an agent for that lane.

Given the owner who said merge to a lane's merge ask, needs an induced failure: main moves and the lane branch takes a merge of main with no conflict after the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the lane's pull request merged by the supervisor at the new head with required checks passing, and the director's tab shows the supervisor's done report naming both the approved head and the merged head.

Given the owner who said merge to a lane's merge ask, needs an induced failure: a fix commit lands on the lane branch after the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the pull request still open and unmerged, and the owner receives a new merge ask from the director naming the new head.

Given any change on a lane, When its supervisor sends the merge ask, Then a code reviewer from a different model family than the implementer, started fresh for that head, has judged it, and no worker reviewed its own work.

Given the owner with an accepted spec built into a lane, When the lane's supervisor changes that spec to clarify a criterion, then the owner reads the lane's merge ask, Then the merge ask lists that change as a judgement call naming what changed, why, the criterion it touches, the role that made it and its evidence, for the owner to approve or deny, and no new spec review was asked.

Given the owner with an accepted spec built into a lane, When the lane's supervisor changes that spec to add a criterion, then the owner reads the lane's merge ask, Then the merge ask flags that call as added scope, apart from the calls it only lists.

Given the owner with an accepted spec built into a lane, When the lane's supervisor changes that spec to weaken one of its criteria, Then the owner receives a message from the director naming that call before the lane's merge ask, the lane keeps running, and the merge ask flags that call again.

Given a lane that has logged three calls, When its supervisor logs a fourth, Then the owner receives a message from the director saying the lane has made more than three calls, and the lane keeps running.

Given the owner who denies one call in a lane's merge ask, When the director relays that denial to the lane's supervisor, then the owner opens the lane's pull request, Then the spec no longer carries that call's change, and the call log shows the call denied with the role that made it.

Given any spec that differs from its accepted commit by a change no logged call names, When just check runs, Then the gate fails and its message names the spec and the unlogged change, proven by an integration test: no screen shows it.

Given any spec whose call log holds a call with an empty or missing evidence field, When just check runs, Then the gate fails and its message names that call, proven by an integration test: no screen shows it.

Given the owner with a work item whose behavior the spec on main already states, When the owner tells the director to build it, then opens the lane's pull request, Then no spec review was asked and no spec pull request opened, and the lane's pull request shows the work, a review verdict, passing required checks and the criteria it flips to built.

Given a finding class that code review has logged as blocking in two lanes, When a supervisor next archives its merged lane, then the director starts the correction lane, Then the tracker of the repository that owns the class's route shows a new parent issue for a correction lane naming that class, Herdr shows its workspace with one corrector, and every product lane keeps running.

Given the owner who corrects an agent's work at a merge gate, When the director handles that correction, Then the target's tracker shows a new correction lane's parent issue quoting the owner's correction.

Given the director whose log holds a reflection finding of class reflection-missed, When the director handles that finding, Then the kit's tracker shows a new correction lane's parent issue quoting the finding and naming the question list as what it changes.

Given a finding class code review has logged as blocking in two lanes that the director reflection routed to a role, skill, template or structure, When the director starts its correction lane, Then the correction lane's parent issue in the kit's tracker names that route as where the fix goes.

Given the director whose checkout of the target is clean on its default branch and behind main, When a lane's pull request merges, then the director runs its post-merge routine, Then the director's checkout is at the merge commit.

Given the director whose checkout of the target holds uncommitted changes, When a lane's pull request merges, then the director runs its post-merge routine, Then the checkout and its changes are as they were, and the routine's report names the checkout and why it did not move.

Given the director, started by hand, with two live agents of one role, one launched before a merged change to that role's file and one launched after it, When the director asks which agents run on a stale launch set, Then the answer names the first agent as stale with its pane, its role and the changed role file, names the director as unknown, and does not name the second agent.

Given a supervisor whose lane's final head has a clear review verdict and green checks, with no spec call, no failed criterion, no opt-out, no owner decision line and no changed path its repository's code owners file gives to the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 1, merging without the owner.

Given a supervisor whose lane's only spec call clarifies a criterion, on a final head holding nothing else for the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 2, naming that call as its reason.

Given a supervisor whose lane holds one behaviour-neutral opt-out that the clear review verdict names by its commit as cleared, on a final head holding nothing else for the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 2, naming that opt-out as its reason.

Given a supervisor whose lane holds one behaviour-neutral opt-out that the clear review verdict does not name, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that opt-out's commit as its reason.

Given a supervisor whose lane's spec call adds a criterion and links no ruling of the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that call as its reason.

Given a supervisor whose lane's spec call weakens a criterion and links no ruling of the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that call as its reason.

Given a supervisor whose lane's spec call adds a criterion and links the owner's written ruling, made before the call, which the review verdict says covers the change, When the supervisor runs the merge ask check, Then the merge ask reads tier 2, naming that call and the ruling it links.

Given a supervisor whose lane's spec call adds a criterion and links the owner's written ruling, which the review verdict does not say covers the change, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that call as its reason.

Given a supervisor whose lane's merge ask lists a criterion the product judge failed, with its triage, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that criterion as its reason.

Given a supervisor whose lane's clear review verdict carries an owner decision line, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, showing that line as its reason.

Given a supervisor whose lane changes a path its repository's code owners file gives to the owner, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming that path as its reason.

Given a supervisor whose lane holds a clarifying spec call and a criterion the product judge failed, When the supervisor runs the merge ask check, Then the merge ask reads tier 3, naming both as its reasons.

Given a supervisor the director named for a spec pull request whose spec is the accepted commit with only its status file added, When the supervisor runs the merge ask check, Then the merge ask reads tier 1, merging without the owner.

Given a supervisor whose lane's merge ask reads tier 2 and names no open pull request its merge would set back, When the supervisor merges the lane with the kit's merge command, then opens the lane's pull request, Then the pull request shows merged by the supervisor at the head the merge ask named, with no relay from the director and no merge from the owner asked for.

Given a supervisor whose lane's merge ask reads tier 1 and names an open pull request its merge would set back, When the supervisor runs the merge ask check, Then the merge ask says its merge waits for the director's order, naming that pull request.

Given a supervisor whose lane's merge ask reads tier 2 and waits for the director's order, When the supervisor sends the merge ask up, then merges on the director's relay, then opens the lane's pull request, Then the pull request shows merged by the supervisor at the head the merge ask named, with no merge from the owner asked for.

Modular boundaries

An owner chat owns shaping, using Spec Chat's shaping skill on the spec's own branch; the review host owns the acceptance record. Caller-facing seam: the accepted spec path and its acceptance on the review host. Dependency direction: external-provider; the factory reads acceptance and never shapes. Observable scope: the review page and its Accept spec action.

The director owns kickoff: checking acceptance, opening the spec pull request with its generated status file (its only repo write), cutting lanes, filing parent issues, branching lanes from main, and starting correction lanes. Caller-facing seam: the owner's build request, octo-feather-accepted SPEC_PATH (exit 0 with the accepted commit, else the reason), and the director's lane start, octo-feather-lane start. Dependency direction: external-provider; it uses the review host, GitHub, the tracker skill and the Herdr wrappers. Observable scope: spec pull requests, parent issues and lane workspaces.

The supervisor role and the vendored implement-spec skill own one lane: tickets, the pilot, briefs, the merge ask and the merge. Caller-facing seam: the lane brief the director sends, the merge ask the supervisor sends back, and the merge the director relays. Dependency direction: external-provider; the supervisor uses the integrate script, the Herdr wrappers, GitHub and the tracker skill, and nothing calls it but its director. Observable scope: the lane's workspace, its sub-issues and pull request.

The integrate script owns landing named worker branches or commits on one lane branch with a green gate, all or nothing: the fast tier, or the full gate at a checkpoint (checkpoints), recording each full pass. Caller-facing seam: just integrate N REF... and its exit status (0 landed, 1 conflict, 2 red gate). Dependency direction: self-contained over git and the target's just fast and just check; it never pushes and calls no model. Observable scope: the lane branch head.

GitHub owns spec and lane pull requests and merges, and the target's tracker, GitHub Issues or Linear, owns parent issues and sub-issues, together the durable record of delivery. Caller-facing seam: the github-pr skill for pull requests and merges, and the tracker skill's scripts for issues (skills). Dependency direction: external-provider. Observable scope: issues in the tracker, pull requests and merge commits.

The status script owns the status file and the call log beside each accepted spec: creating the status file, flipping criteria to built, checking it against the spec, and checking that every change to the spec since its accepted commit is named by a logged call. Caller-facing seam: octo-feather-spec-status init SPEC COMMIT, built STATUS PR ID... and check [DIR...], the last inside just check. Dependency direction: self-contained over the spec HTML, its git history, its status file and its call log; it never edits the spec and calls no model. Observable scope: docs/specs/<slug>.status.json, docs/specs/<slug>.calls.jsonl and the gate's message.

The merge ask check owns sorting a merge ask into its tier. Caller-facing seam: octo-feather-lane merge-ask PR, which prints the tier, each reason and whom the merge waits for with the merge ask. Dependency direction: external-provider; it reads GitHub for the review verdict, the checks and the pull request's commits and paths, and the lane worktree for the spec call logs, the qc results and the repository's code owners file; it calls no model. Observable scope: the tier and its reasons, printed with the merge ask.

The digest command owns the daily list of merges and their tiers. Caller-facing seam: one kit command the director runs for a day. Dependency direction: external-provider; it reads the merged pull requests' merge asks from GitHub and calls no model. Observable scope: the digest the director sends the owner.

The lane start's brake owns whether a new lane may start, on the Claude account's usage and the box's room. Caller-facing seam: the refusal of the director's lane start, octo-feather-lane start. Dependency direction: external-provider; it reads the account's usage as the model provider reports it on the box's model route, the box's lane records and the box's settings; no model decides. Observable scope: the supervisor started, or the refusal naming what it read.

The line

Lanes and tickets

One lane is one supervisor, one merge ask and one parent issue in the target's tracker, filed by the director. The director cuts lanes from the accepted spec with no numeric cap: usually one spec is one lane; a big spec whose outcomes can merge independently becomes several; several small coupled specs become one; code that must change together stays in one lane.

The lane start, octo-feather-lane start, also refuses a new lane, naming what it read, in two cases. The first is usage: the Claude account's weekly use is on course to pass the box's reserve before the weekly reset. The reading is the provider's own report for the account, the share of its weekly limit used and the time that limit resets, so it counts every use of the account, the owner's own included; of the weekly windows the provider reports, the tightest decides. The course is that share plus the burn to the reset, at the higher of the week's average burn so far and the burn of the last hours. The reserve is a share of the provider's weekly limit, a tenth unless the box's settings say otherwise, so the owner names no budget. When a reading cannot be had, the lane start carries the last reading of the same week forward at the burn measured while readings came, and decides on that, saying so. With no reading since the last reset it refuses nothing: the lane starts, and the start says the usage could not be read, since a factory stopped by a failed reading costs more than a week that runs short. The second is room: the box already holds its limit of open lanes, seven unless the box's settings say otherwise, an open lane being one not yet archived, those waiting on the owner included. Lanes already running keep running. No model takes part, and there is no override: the reserve and the lane limit are the box's settings, the owner's to change (#acceptance-lane-start-usage, #acceptance-lane-start-room).

Later slice, with the kit's watchdog: readings on a schedule while no lane starts, one fixed message to the director each time a line is crossed, idle lanes parked once the use itself reaches the reserve, and lane starts resumed after the weekly reset, with no person in the loop.

The supervisor decides ticket count, order, cuts and the worker split. Tickets are sub-issues of the lane's parent, with Blocked by only where order matters. Every ticket is a tracer bullet: a thin path through every layer, ending on a demo path through a public interface the product offers its users (its CLI, HTTP, UI, MCP or another public protocol), or the target's runnable script when it has none (ADR 0002), naming the acceptance criteria it serves; a ticket that serves none, such as a fix to a rule an ADR or an owner ruling owns, names that rule and its owner instead. Every ticket names the skills its worker must load in one Skills: line (Skills: none when it needs none), checked to be skills the worker's role is offered; a ticket without the line fails the ticket check. When the supervisor consumes a worker's result it compares that line with the worker's Pi session: a named skill whose file the session never loaded is a miss, logged in the lane's hand-off log, and the first miss of a skill on a ticket sends the worker back once to load it before its work is integrated; a miss after that send-back is recorded and the work goes on. The comparison proves a load, never that the skill was applied or that the line named the right skills; review judges those.

The first ticket is the pilot: it runs alone through brief, one implementer and just integrate; then the supervisor opens the lane's draft pull request, and runs just qc on the pilot's criteria and a fresh code review of the same head, in parallel. The supervisor then fixes its brief template, re-cuts the remaining tickets and fans out.

After the pilot the supervisor runs implementers in parallel, one per ready ticket, whenever tickets do not block each other and it judges parallel work practical.

After integration the supervisor runs just qc, naming every criterion the lane builds, and a fresh code review in parallel, both on the integrated head H; neither waits for the other. As they start, the supervisor pushes H with the lane's pull request ready for review, so CI's full run on H goes alongside them, never after them. qc's status-only commit makes H′, the head the merge ask names with both verdicts, and a check fails unless H to H′ changes only the status files qc writes, naming any other file (ADR 0022). A push that adds only such status-only commits starts no new CI full run, and the merge ask takes the checks of the head they follow, under the same check (#acceptance-ci-alongside, #acceptance-ci-status-only). Both run to their verdicts: one that fails first never stops the other, so one implementer repairs the blocking findings of both at once, and then both run again in parallel on the new head. Any other code change after qc means qc again, except a merge of main that a check proves brought in nothing but main's changes: the lane's own diff against the new main is identical to its diff at the judged head, hunk by hunk wherever main's changes elsewhere in a file moved its lines, with no conflict resolved. That merge keeps the qc verdict with no new judge run, and the merge ask names the judged head, the refreshed head and the check's proof (owner gates). A merge of main that resolved a conflict, or changed anything beyond git's automatic merge, keeps the review verdict once a fresh code review of that merge's resolution alone, what git show --remerge-diff prints for it, is clear: the reviewer reads only the resolution, never main's changes, which main's own review already judged, and the merge ask names the reviewed head, the merge and the resolution's verdict. just qc then runs on the new head as quality #qc-carry says (#acceptance-review-resolution). The code reviewer judges the lane's code quality; just qc judges the criteria. Only criteria that pass are built. The supervisor never edits a criterion's status by hand. A lane whose brief names no criterion, such as a fix to a rule an ADR or an owner ruling owns, builds none and runs no just qc: the fresh code review alone judges its integrated head, the merge ask names that head and says the lane builds no criterion, and a merge of main that the same check proves clean keeps the review verdict. The review verdict the merge ask reads covers the whole lane: every review round posted to the pull request names the range its reviewer diffed, the first from main and each later one from the head the round before it ended on, so a review of a fix adds to the earlier rounds' check classes and never replaces them (#acceptance-verdict-covers-lane). The merge ask shows each check the review verdict classes a declaration (ADR 0008 rung 2) apart from exact checks, as a stopgap for the owner (#acceptance-declaration-check-shown).

Inside a lane the fast tier, just fast, checks each change, and a head only it passed is provisional. The full gate, just check, runs at each checkpoint, on the candidate head before just integrate accepts it, rolling back on red: the lane's first integration (the pilot); any integration whose diff touches a path the repository's shared-machinery list names, by adding, deleting or either side of a rename, judged against the list before the integration and its newly added entries; any change to that list; and the lane's final head, before qc, review and the merge ask, in every lane, one that builds no criterion included. Each full pass is recorded against its head, the gate's configuration and the list's identity. The merge ask check refuses a head without a current full pass; a status-only commit after the pass and a merge of main the one-head check proves clean keep it. The list is ordinary repository policy the factory keeps: a lane that adds or moves shared machinery updates it in the same change, the code reviewer judges its completeness, and test impact analysis from recorded coverage leaves on it only what coverage cannot see, such as configuration, pins and workflow files. It schedules full runs; it is no proof that an unlisted change has no wider effect, and running the full gate more often is never refused. A repository with no fast tier, such as one the kit did not create, runs its own single gate as the full tier at every integration and gains no recipe. CI stays a separate full run. The merge ask shows the full gate's wall time on the final head against the repository's gate-time budget, with its trend and slowest items, flagged when over the budget or grown by more than the set share; the code reviewer judges it, and no gate decides on timing.

just qc STATUS... PR ID... runs scripts/octo-feather-qc (ADR 0022), one run for the lane's criteria in every spec it builds, each id in exactly one named status file's spec, so the final head's one full gate serves them all: it captures each named criterion's declared demo at the lane head into the evidence store, then judges each criterion only from its record, one pass, fail or insufficient evidence each, with a fresh agent judge only for a criterion that declares no demo (quality #qc-run). The script, never a model, then commits only the status files, in one commit: each passed criterion built with the lane's pull request, the others planned. It refuses a fallback judge of the implementer's model family, a dirty worktree, a result set that does not name exactly the claimed ids, and a run that changed files. Nothing in the run holds a tracker credential: it reads the pull request and its GitHub snapshot, never Linear.

A correction lane is an ordinary lane whose work is factory quality: the director starts one when the owner corrects something at a gate, when code review or the product judge has logged a blocking finding of one class in the hand-off logs of two or more lanes, or on a reflection finding of class reflection-missed, whose fix is the question list (comms #reflection-questions). The reflection at each lane archive applies these rules and files the parent issue of each correction lane due (comms #reflection-correction); the director starts the lane. A reflection's own finding is never blocking: it names a class and a route but makes no lane due, except reflection-missed, so a lane starts only on a repeated real failure. A correction lane for a class the director reflection routed names that route, so the fix lands where the work is written as well as in review. A class that already has a correction-lane issue, open or closed, starts another only on a finding of that class dated after that issue closed. A finding of a class whose issue is open: comms #reflection-correction. It has its own parent issue, supervisor, one corrector, code review and a small merge ask, and no product lane waits on it (ADR 0020). Before its merge ask, a correction lane replays each check it adds on the failures that made it due: one row per finding its parent issue lists, or its trigger as the one row when the issue lists none, and a row per clean lane in a sample the merge ask check picks by a fixed rule; the check reruns each row itself and shows how many findings the new check caught and how many clean cases it refused, and the owner judges the count (#acceptance-correction-replay-missing, #acceptance-correction-replay-shown).

Owner gates

Spec acceptance is the owner's gate, and so is any acceptance of unaccepted work. A merge is the owner's gate only when its merge ask sorts to tier 3 (tiers): every other merge goes ahead without the owner, who reads it in the daily digest and may veto it there. No agent decides a gate that is the owner's, and no agent sorts a merge ask. Promotion and live traffic changes for merged work belong to the director under owner delegation; one carrying a consequential product or risk decision goes to the owner.

The merge ask check sorts every merge ask, a spec pull request's included, into one tier, and prints the tier with each reason it found and whom the merge waits for: nobody, the director's order, or the owner. It reads only records the lane already has: the review verdict, the pull request's checks, the spec call logs, the commits and the paths they change, the qc results and the repository's code owners file. The highest tier any reason gives is the ask's tier. Any agent may raise an ask's tier by adding a reason; only the check lowers one, and no agent's reading of an ask sorts it (ADR 0033).

A repository names the paths that wait for its owner in its code owners file, CODEOWNERS, the file its Git host already reads for who approves a path: a path whose owners include the repository's owner waits. A repository that names none gates none by path, and the kit's own names none: a risky change to the kit is proven by its gate and its product judge, never by the owner's reading. The Git host's own required code owner review stays off, since the factory merges under the owner's account.

A ruling the owner gave once does not return at merge. The call links where the ruling is written, an issue or a comment on one, dated before the call; the check reads that the link is there and is older, and the code reviewer says in its verdict whether the ruling covers the change. A call that only says the owner agreed stays tier 3.

The lane's supervisor merges a tier 1 or tier 2 ask itself, with its merge command, pinned to the head the ask named, when the ask names no open pull request the merge would set back (merge order): the tier is the approval that merge needs, and the supervisor sends nothing up first. When the ask names one, its merge waits for the director's order: the supervisor sends the ask up, and the director relays the merge in the order it decides, without asking the owner. A tier 3 ask always goes up: the director relays it to the owner, waits for the owner's merge and relays that.

Once a day the director sends the owner one merge digest, made by a kit command from the merged pull requests' merge asks and never written by hand: each tier 2 merge with its pull request, its calls and its opt-outs in full, and each tier 1 merge in one line. The owner may veto any merge it lists. A veto reverts nothing by itself: the director starts an ordinary lane that reverts or repairs the merge, and a vetoed call is a denied call (call decision).

Shaping and spec acceptance happen outside the factory: the owner's chat shapes the spec and registers it under the spec's own slug, and the review host's acceptance is the record. Spec acceptance is only the owner pressing Accept spec on the review page: an acceptance said in chat is not one, and no agent records an acceptance for the owner. The factory starts when the owner tells the director to build an accepted spec.

Every later gate reaches the owner through the director: the supervisor sends a review link or the merge ask up with herdr-say --parent and never addresses the owner (ADR 0015).

The lane's supervisor alone performs a merge, with its merge command, pinned to the head the merge ask named: by itself for a tier 1 or tier 2 ask that waits for nobody, and on the director's relay, which names that head, for an ask that waits for the director's order or for the owner (who merges). Main moving does not move the lane's head: only a push to the lane branch does. When the only commits added since the merge ask are merges of main into the lane branch that the one-head check proves clean, and required checks pass on the new head, the supervisor merges pinned to the new head without a new merge ask, runs no new qc, and names both heads in its done report. Any other change to the head, a fix commit, a rebase or a resolved conflict, and any failed merge, is never forced: the supervisor reruns its gates, just qc on every criterion the change affects included, the review as one head scopes it, and sends a new merge ask. A merge of main is preferred to a rebase, which rewrites the approved commits. The integrate script never takes part: it lands worker branches on the lane branch only and never pushes. A spec pull request merges the same way: the director names a supervisor for it, its merge ask is sorted like any other, one whose spec is the accepted commit with only the status file added sorting to tier 1, and that supervisor merges it as it would a lane's; neither the owner nor the director merges it.

For the director's merge order, the merge ask check also names each other open lane pull request this lane's merge would set back: each whose product judge demos pin stored eval runs that this lane's changes would make stale on main (roles), with those runs and the changed files, and each whose head conflicts with this lane's head, with the conflicting files. It only names them: the check passes or fails the same without them, and the director decides the order.

A lane pull request's body names its parent issue with the tracker skill's pr-line: Closes #N on GitHub, Tracks <KEY> on Linear, and the merge ask check accepts either. After the merge the supervisor moves the parent issue and every ticket to done with the tracker skill's issue-done, whether or not the tracker already did.

After a lane merges, its post-merge routine carries main's move to what runs from it, then closes the lane, with no command from the director. The supervisor's merge command performs the merge an approval already allowed, adding no merge policy of its own, and starts the routine; the lane's archive waits until the routine has refreshed the kit install for that merge, then starts the lane's teardown (comms teardown). The routine records each step as done, stopped or pending, a rerun resumes at the first step not done, and the routine shows that record on demand. The kit install, on its default branch or detached, and the director's own checkout of the target, the main checkout of the repository the routine runs in, on its default branch, each move to the merge commit only by a fast-forward; one already at or past it stays. Before either moves, one that holds uncommitted changes, is on another branch or has diverged is left as it is and named with the reason, as the routine's stop, for the director to resolve and rerun. The routine then starts the coverage map's rebuild where the repository has one (quality #acceptance-map-after-merge). The routine then lists each live agent whose launch set is stale (roles): its pane, its role and each file that differs, and each agent whose launch set is unknown, a director started by hand among them. It relaunches no agent: whether and when one relaunches is its director's or supervisor's call. The director gets the same list on demand at any time. A step that would change files a live eval, gate or qc run reads, each found from the box's run slots, waits for that run, then stops naming it. A stopped step tells the director once, naming why. A red main CI on the merge commit is such a stop, and the lane's archive waits until a later main CI run that contains the merge passes. When the teardown ends, the director gets one message for the merge carrying what a close report carries: the tickets done, what is left open and where, the reflection's finding counts, the correction lanes filed or commented, and anything left on disk on purpose. A supervisor that never archives leaves the routine pending, as its record shows.

The review page's Accept hand-off, for the spec at the registered commit, is the record of spec acceptance. The accepted spec merges to main before any lane code, in its own spec pull request whose body cites the acceptance id and commit. Beside it sits docs/specs/<slug>.status.json: the spec file, the accepted commit, and each criterion's status, planned or built, keyed by the data-anchor of its data-acceptance-criterion element, with the pull request that built it and, once built, the evidence record it was judged from, the commit that record was captured at and the tests that enforce it. A criterion starts planned when first added. Initializing the status of an owner-accepted revision starts from the existing status file: it keeps each matching criterion's row with its pull request and evidence, adds new criteria planned, drops criteria the revision removed and moves the accepted commit to the revision; invalid existing status refuses with nothing written, and repeating it changes nothing. Each lane pull request flips only its own criteria to built, in the same merge as its code; just qc writes that flip for the criteria it passed (ADR 0022). Built means just qc passed it on evidence captured at that commit; it goes stale as quality #qc-stale says. The spec file itself never changes for status.

After acceptance a spec changes only by a logged judgement call, and the spec and the code change together: the lane keeps working, no new spec review is asked, and the owner's acceptance stays the baseline, so the status file's accepted commit does not move. Only the supervisor edits the spec and logs the call; an implementer or corrector that needs a spec change asks its supervisor, so no agent approves its own shortcut or extra work. Each call, in the call log beside the spec, records what changed, why, the criterion it touches, the role that made it and its evidence. A call that adds a criterion adds it to the status file as planned, and one that removes a criterion drops it.

  1. Before any spec edit the call answers: can the accepted criteria pass with the spec as written? If they can, there is no edit.
  2. Each call cites evidence: a failing command, an error, or two spec lines that contradict each other. No evidence, no call.
  3. Additions are proposals, not calls: a new feature, extra case or future-proofing goes to docs/future.md or an issue, and the work goes ahead without it, unless an existing criterion cannot pass without it.

In a tier 3 merge ask the owner approves or denies each call, and the owner's merge approves every call not denied. A denied call goes back to the lane as rework, and the call log records the denial with the role that made the call, so the role that overreaches gets its prompt fixed. just check diffs each spec against its accepted commit itself and fails on any change no logged call names, so the record never rests on agents reporting their own edits.

A work item whose behavior the spec on main already states needs no shaping, no new acceptance, no kickoff check and no spec pull request: it goes straight to a lane, which flips that spec's criteria it builds in the status file on main.

Before the merge ask, the supervisor triages every product criterion the product judge failed: a failure whose evidence state is complete is a code fault unless the triage names a specific capture cause, such as a wrong fixture, a wrong screen reached or the criterion's shape; a code fault gets a repair ticket worked by a fresh implementer; a capture cause is fixed and re-judged; a failure in behavior the lane did not change is listed as outside the lane with the reason. Every verdict the merge ask lists was judged at the lane's judged head (one head).
