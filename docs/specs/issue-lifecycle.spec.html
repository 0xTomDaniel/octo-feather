Issue lifecycle: spec to merge

docs / specs / issue-lifecycle.spec.html

How one work item moves through the factory, which steps stop the line, and what the owner decides. Roles are in roles; messages and lane state in comms; the gate recipes in quality.

User stories

As the owner, nothing is built for a work item until I accept its spec, so I approve what the work must do before agents spend on it.

As the owner, I get one merge ask per work item, relayed by the director, that already carries every piece of evidence I need to decide.

As a supervisor, I combine my workers' branches with a script that either lands all of them with a green gate or lands nothing, so conflicts never get resolved by guesswork.

As the owner, a wording-only correction to a spec I accepted rides on my acceptance, while any change to what the spec makes the system do comes back to me.

As the owner, a ticket whose behavior the spec on main already states goes straight to delivery with no new spec review.

Acceptance criteria

Given a supervisor with a shaped spec under review, When the owner opens the work item's workspace before pressing Accept spec, Then the workspace shows the supervisor tab and no implementer tab.

Given the owner with a spec under review, When the owner presses Accept spec, then opens the work item's pull request, Then the pull request shows one receipt comment quoting the action, its date, the spec path, the accepted commit, and who recorded it.

Given a supervisor with two finished implementer branches that change the same lines, When the supervisor integrates both, Then the lane branch is where it was before the second merge and the supervisor is told it stopped on a conflict, proven by an integration test: no screen shows it.

Given a supervisor with a finished implementer branch that turns the gate red, When the supervisor integrates it, Then the lane branch is where it was before and the supervisor is told the gate is red, proven by an integration test: no screen shows it.

Given a work item whose final head passed review, When the owner reads the merge ask the director relays, Then it names the head, shows required checks passing, links the review verdict and the spec acceptance receipt, and lists every failed product criterion with its triage.

Given any change on a work item, When its supervisor sends the merge ask, Then a code reviewer from a different model family than the implementer, started fresh for that head, has judged it, and no worker reviewed its own work.

Given the owner with an accepted spec, When the supervisor commits a correction that only rewords that spec, then the owner opens the pull request, Then the pull request body names that commit as wording-only in one line, and the pull request shows no new acceptance receipt for it.

Given the owner with an accepted spec, When the supervisor commits a spec change that alters a behavior the spec states, Then the owner receives a review link for that change from the director before any merge ask.

Given the owner with a ticket whose behavior the spec on main already states, When the supervisor delivers it and the owner opens the pull request, Then no spec review was asked, and the pull request shows the ticket's work, a review verdict, and passing required checks.

Modular boundaries

The supervisor role and the vendored implement-spec skill own the order of steps, briefs and the merge ask. Caller-facing seam: the brief the director sends and the merge ask the supervisor sends back. Dependency direction: external-provider; the supervisor uses the integrate script, the Herdr wrappers and GitHub, and nothing calls the supervisor but its director. Observable scope: the lane's workspace, the work item's issues and pull request.

The integrate script owns landing named worker branches or commits on one lane branch with a green gate, all or nothing. Caller-facing seam: just integrate N REF... and its exit status (0 landed, 1 conflict, 2 red gate). Dependency direction: self-contained over git and the target's just check; it never pushes and calls no model. Observable scope: the lane branch head.

GitHub owns issues, pull requests, receipts and merges as the one durable record. Caller-facing seam: the gh CLI. Dependency direction: external-provider. Observable scope: issues, pull request comments and merge commits.

Owner gates

Spec acceptance and merge are the owner's gates, and so are any acceptance of unaccepted work, promotion and live traffic changes. No agent decides any of them.

Every gate reaches the owner through the director: the supervisor sends the review link and the merge ask up with herdr-say --parent, and never addresses the owner (ADR 0015).

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the work item's pull request, and everything that needs it reads that comment. The receipt quotes the owner's words or page action, gives the date, names what is accepted and the exact commit, and who recorded it. A spec accepted on the review page is recorded by the supervisor processing that hand-off; a spec accepted in chat is recorded by the director; delivered work is recorded by the agent receiving the merge instruction, before it merges.

A spec commit after acceptance that changes only wording, labels or anchors, adds or removes no criterion, and changes no stated behavior, value or outcome keeps the original acceptance. The supervisor decides and lists each such commit in the pull request body; a commit it cannot plainly call wording-only goes back for a fresh acceptance.

A ticket whose behavior the spec on main already states needs no shaping and no new acceptance: that spec's commit on main is the acceptance receipt, and one implementer, the corrector and one code reviewer still run.

Before the merge ask, the supervisor triages every product criterion the product judge failed: a code fault gets a repair ticket worked by a fresh implementer; a fault in how the criterion was judged is fixed and re-judged; a failure in behavior the lane did not change is listed as outside the lane with the reason. Every verdict the merge ask lists was judged at the merge ask's head.
