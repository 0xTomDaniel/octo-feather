Lifecycle: accepted spec to merge

docs / specs / issue-lifecycle.spec.html

How an accepted spec becomes lanes, how one lane moves to its merge ask, which steps stop the line, and what the owner decides. A lane is one merge ask on one parent GitHub issue (ADR 0019). Roles are in roles; messages and lane state in comms; the gate recipes in quality.

User stories

As the owner, I shape and accept a spec in my own chat before the factory sees it, and the factory builds only a spec I accepted.

As the owner, each lane reaches me as one merge ask on one parent issue, relayed by the director, already carrying every piece of evidence I need to decide.

As the owner, when I say merge, the work I approved lands on main as I approved it: the head I approved, or that head with only a clean merge of main into it, and any other change to the lane comes back to me as a new merge ask instead of being forced through.

As the owner, main tells me which criteria of each accepted spec are planned and which are built, and by which pull request, without the spec I accepted changing.

As the owner, every ticket on a lane is a thin path I could demo, so progress on the parent issue means working behavior, not half-built layers.

As a supervisor, my first ticket runs alone end to end, so a bad brief, check or ticket size fails once instead of in every worker.

As the owner, the code review I read in a merge ask judged the exact head I would merge, the one whose built claims the product judge wrote.

As a supervisor, I combine my workers' branches with a script that either lands all of them with a green gate or lands nothing, so conflicts never get resolved by guesswork.

As the owner, a wording-only correction to a spec I accepted rides on my acceptance, while any change to what the spec makes the system do comes back to me.

As the owner, a work item that the spec on main already states goes straight to a lane with no new spec review.

As the owner, a mistake that repeats gets fixed in the factory once, in its own lane, without holding up product work.

Acceptance criteria

Given the owner with a spec that has not been accepted, When the owner tells the director to build it, Then the director tells the owner the spec is not accepted and why, and GitHub shows no new parent issue and Herdr no lane workspace or supervisor tab for it.

Given the owner with an accepted spec, When the owner tells the director to build it, Then GitHub shows a spec pull request from spec/<slug> whose only commit after the accepted one adds docs/specs/<slug>.status.json with every criterion planned, its body cites the acceptance id and the accepted commit, and no lane parent issue exists while it is open.

Given the owner who tells the director in chat that a spec is accepted without pressing Accept spec, When the owner tells the director to build it, Then the director refuses it as not accepted, naming the Accept spec button as the only way to accept, and no spec pull request opens.

Given the owner with an accepted spec, When the owner merges its spec pull request, Then GitHub shows one new parent issue per lane the director cut, and Herdr shows one lane workspace per parent issue holding its supervisor.

Given the owner who merged a spec pull request, When a lane for that spec opens its draft pull request, then the owner opens it, Then the lane branch starts from a main that holds the spec and its status file, and the spec file in the pull request is byte-identical to the accepted commit's.

Given a lane whose merge ask lists the criterion ids it builds, When the owner merges it, then opens the spec's status file on main, Then exactly those criteria read built with that pull request's number, in the same merge commit as the lane's code, and every other criterion is unchanged.

Given a status file whose ids differ from its spec's criteria by one missing, extra or duplicated id, or that marks a criterion built without a pull request, When just check runs, Then the gate fails and its message names the status file and the offending id, proven by an integration test: no screen shows it.

Given a supervisor starting a lane, When it files the lane's tickets, then the owner opens the lane's parent issue, Then the parent issue lists every ticket as a sub-issue, and a ticket shows Blocked by only where it must wait for another.

Given a supervisor, When any lane's tickets are filed, Then every ticket names the acceptance criteria it serves and ends on a demo path through the app's CLI, HTTP or UI, and none is a layer-only ticket outside a wide refactor's expand-and-contract sequence.

Given a supervisor with several ready tickets, When it starts delivery, then the owner opens the lane's workspace, Then the workspace holds one implementer tab, for the first ticket, and no second implementer tab appears until that ticket has been integrated and reviewed.

Given a supervisor whose pilot ticket was just integrated, When it sends the pilot's results up, then the owner opens the lane's draft pull request, Then the pull request exists, its status file marks the pilot's passed criteria built with that pull request's number in a status-only commit, and the pilot's review verdict names the head that commit made.

Given a lane ready for its merge ask, When the owner reads the merge ask, Then the head it names is the one just qc left, its last commit changes only the status file, the qc report named every criterion the lane builds, and the code review verdict names that same head.

Given an integrated lane head whose lane builds three criteria, When the supervisor runs just qc naming all three and one fails, Then the qc report shows one pass or fail per named criterion, each with the command run and its output, from a code reviewer started fresh and headless for that run, and the new head's only change is the status file, marking the two passed criteria built and the failed one planned.

Given a supervisor past its pilot with two ready tickets that do not block each other, When it fans out, then the owner opens the lane's workspace, Then the workspace shows two implementer tabs working at the same time.

Given a supervisor with two finished implementer branches that change the same lines, When the supervisor integrates both, Then the lane branch is where it was before the second merge and the supervisor is told it stopped on a conflict, proven by an integration test: no screen shows it.

Given a supervisor with a finished implementer branch that turns the gate red, When the supervisor integrates it, Then the lane branch is where it was before and the supervisor is told the gate is red, proven by an integration test: no screen shows it.

Given a lane whose final head passed review, When the owner reads the merge ask the director relays, Then it names the head, shows required checks passing, gives each criterion's qc verdict and links the review verdict, lists the criterion ids qc flipped to built, and lists every failed product criterion with its triage.

Given the owner who said merge to a lane's merge ask, with the lane branch unchanged since the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the lane's pull request merged by the supervisor at the head the merge ask named, and its parent issue closed.

Given the owner who said merge to a lane's merge ask, needs an induced failure: main moves and the lane branch takes a merge of main with no conflict after the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the lane's pull request merged by the supervisor at the new head with required checks passing, and the director's tab shows the supervisor's done report naming both the approved head and the merged head.

Given the owner who said merge to a lane's merge ask, needs an induced failure: a fix commit lands on the lane branch after the merge ask, When the director relays that merge to the lane's supervisor, Then GitHub shows the pull request still open and unmerged, and the owner receives a new merge ask from the director naming the new head.

Given any change on a lane, When its supervisor sends the merge ask, Then a code reviewer from a different model family than the implementer, started fresh for that head, has judged it, and no worker reviewed its own work.

Given the owner with an accepted spec built into a lane, When the supervisor commits a correction that only rewords that spec and renames one criterion anchor, then the owner opens the lane's pull request, Then the pull request body names that commit as wording-only in one line, no new spec review was asked, and the same commit renames that criterion's key in the status file, keeping its status.

Given the owner with an accepted spec built into a lane, When the supervisor needs a spec change that alters a behavior the spec states, Then the owner receives a review link for that change from the director before any merge ask, naming each criterion id the revision affects, and once the owner accepts it, the status file's accepted commit is the revision's commit, each named criterion and each criterion it adds reads planned, and each criterion it removes is gone.

Given the owner with a work item whose behavior the spec on main already states, When the owner tells the director to build it, then opens the lane's pull request, Then no spec review was asked and no spec pull request opened, and the lane's pull request shows the work, a review verdict, passing required checks and the criteria it flips to built.

Given a finding class that code review has logged twice across lanes, When the director checks finding classes after the next merge ask, Then GitHub shows a new parent issue for a correction lane naming that class, Herdr shows its workspace with one corrector, and every product lane keeps running.

Given the owner who corrects an agent's work at a merge gate, When the director handles that correction, Then GitHub shows a new correction lane's parent issue quoting the owner's correction.

Modular boundaries

An owner chat owns shaping, using Spec Chat's shaping skill on the spec's own branch; the review host owns the acceptance record. Caller-facing seam: the accepted spec path and its acceptance on the review host. Dependency direction: external-provider; the factory reads acceptance and never shapes. Observable scope: the review page and its Accept spec action.

The director owns kickoff: checking acceptance, opening the spec pull request with its generated status file (its only repo write), cutting lanes, filing parent issues, branching lanes from main, and starting correction lanes. Caller-facing seam: the owner's build request, octo-feather-accepted SPEC_PATH (exit 0 with the accepted commit, else the reason), and the director's lane start. Dependency direction: external-provider; it uses the review host, GitHub and the Herdr wrappers. Observable scope: spec pull requests, parent issues and lane workspaces.

The supervisor role and the vendored implement-spec skill own one lane: tickets, the pilot, briefs, the merge ask and the owner-approved merge. Caller-facing seam: the lane brief the director sends, the merge ask the supervisor sends back, and the owner's merge the director relays. Dependency direction: external-provider; the supervisor uses the integrate script, the Herdr wrappers and GitHub, and nothing calls it but its director. Observable scope: the lane's workspace, its sub-issues and pull request.

The integrate script owns landing named worker branches or commits on one lane branch with a green gate, all or nothing. Caller-facing seam: just integrate N REF... and its exit status (0 landed, 1 conflict, 2 red gate). Dependency direction: self-contained over git and the target's just check; it never pushes and calls no model. Observable scope: the lane branch head.

GitHub owns parent issues, sub-issues, spec and lane pull requests and merges as the durable record of delivery. Caller-facing seam: the gh CLI. Dependency direction: external-provider. Observable scope: issues, pull requests and merge commits.

The status script owns the status file beside each accepted spec: creating it, flipping criteria to built, and checking it against the spec. Caller-facing seam: octo-feather-spec-status init SPEC COMMIT, built STATUS PR ID... and check [DIR...], the last inside just check. Dependency direction: self-contained over the spec HTML and its status file; it never edits the spec and calls no model. Observable scope: docs/specs/<slug>.status.json and the gate's message.

The line

Lanes and tickets

One lane is one supervisor, one merge ask and one parent GitHub issue, filed by the director. The director cuts lanes from the accepted spec with no numeric cap: usually one spec is one lane; a big spec whose outcomes can merge independently becomes several; several small coupled specs become one; code that must change together stays in one lane.

The supervisor decides ticket count, order, cuts and the worker split. Tickets are sub-issues of the lane's parent, with Blocked by only where order matters. Every ticket is a tracer bullet: a thin path through every layer, ending on a demo path through the app CLI, HTTP or UI, or the target's runnable script when it has none (ADR 0002), naming the acceptance criteria it serves.

The first ticket is the pilot: it runs alone through brief, one implementer and just integrate; then the supervisor opens the lane's draft pull request, runs just qc on the pilot's criteria, and starts a fresh code review of the head qc left. The supervisor then fixes its brief template, re-cuts the remaining tickets and fans out.

After the pilot the supervisor runs implementers in parallel, one per ready ticket, whenever tickets do not block each other and it judges parallel work practical.

After integration the supervisor runs just qc on the integrated head, naming every criterion the lane builds; its status-only commit is the head the fresh code review then judges and the merge ask names. So qc and review run on adjacent heads, H and H′, and before the merge ask the supervisor checks that the status commit is the only change between them (ADR 0022). A failed criterion is a blocking finding for an implementer, and any code change after qc means qc again, except a merge of main that resolved no conflict and leaves the lane's own diff unchanged (owner gates). The code reviewer judges the lane's diff; just qc judges the criteria. Only criteria that pass are built. The supervisor never edits a criterion's status by hand.

Until Jev replaces it, just qc STATUS PR ID... runs scripts/octo-feather-qc (ADR 0022): a fresh code reviewer, headless and read-only, judges the whole lane head against each named criterion, runs its demo path, and reports one pass or fail with the command and its output. The script, not the judge, then commits only the status file: each passed criterion built with the lane's pull request, each failed one planned. It refuses a judge of the implementer's model family, a dirty worktree, a report that does not name exactly the claimed ids, and a judge that changed files.

A correction lane is an ordinary lane whose work is factory quality: the director starts one when the owner corrects something at a gate, or when a finding class appears two or more times across lanes. A class that already has a correction-lane issue, open or closed, starts another only on a finding of that class dated after that issue closed. It has its own parent issue, supervisor, one corrector, code review and a small merge ask, and no product lane waits on it (ADR 0020).

Owner gates

Spec acceptance and every merge, spec pull requests included, are the owner's gates, and so are any acceptance of unaccepted work, promotion and live traffic changes. No agent decides any of them.

Shaping and spec acceptance happen outside the factory: the owner's chat shapes the spec and registers it under the spec's own slug, and the review host's acceptance is the record. Spec acceptance is only the owner pressing Accept spec on the review page: an acceptance said in chat is not one, and no agent records an acceptance for the owner. The factory starts when the owner tells the director to build an accepted spec.

Every later gate reaches the owner through the director: the supervisor sends a review link or the merge ask up with herdr-say --parent and never addresses the owner (ADR 0015).

After the owner says merge, the director relays it with the head the merge ask named, and the lane's supervisor alone performs the merge, pinned to that head. Main moving does not move the lane's head: only a push to the lane branch does. When the only commits added since the merge ask are merges of main into the lane branch that resolved no conflict, so the lane's own diff against main is unchanged, and required checks pass on the new head, the supervisor merges pinned to the new head without a new merge ask, runs no new qc, and names both heads in its done report. Any other change to the head, a fix commit, a rebase or a resolved conflict, and any failed merge, is never forced: the supervisor reruns its gates, just qc on every criterion the change affects included, and sends a new merge ask. A merge of main is preferred to a rebase, which rewrites the approved commits. The integrate script never takes part: it lands worker branches on the lane branch only and never pushes.

The review host's accepted registration is the record of spec acceptance. The accepted spec merges to main before any lane code, in its own spec pull request whose body cites the acceptance id and commit. Beside it sits docs/specs/<slug>.status.json: the spec file, the accepted commit, and each criterion's status, planned or built, keyed by the data-anchor of its data-acceptance-criterion element, with the pull request that built it. Every criterion starts planned. Each lane pull request flips only its own criteria to built, in the same merge as its code; just qc writes that flip for the criteria it passed (ADR 0022). Built means claimed, not proven: just qc verifies it. The spec file itself never changes for status.

The supervisor may commit spec corrections that change only wording, labels or anchors, add or remove no criterion, and change no stated behavior, value or outcome; these keep the original acceptance, and the supervisor lists each in the pull request body; a renamed criterion anchor renames its status key in the same commit. Anything it cannot plainly call wording-only is a spec revision made with spec-chat-shape, whose review link goes up through the director for a fresh acceptance before any merge ask; its review link names every criterion the revision affects, including any changed through a clause that governs it, and the code reviewer checks that list's scope. That acceptance moves the status file's accepted commit, resets each named criterion to planned, adds new criteria as planned and drops removed ones.

A work item whose behavior the spec on main already states needs no shaping, no new acceptance, no kickoff check and no spec pull request: it goes straight to a lane, which flips that spec's criteria it builds in the status file on main.

Before the merge ask, the supervisor triages every product criterion the product judge failed: a code fault gets a repair ticket worked by a fresh implementer; a fault in how the criterion was judged is fixed and re-judged; a failure in behavior the lane did not change is listed as outside the lane with the reason. Every verdict the merge ask lists was judged at the merge ask's head.
